# Ambitions Chrome Enrichment Doctrine

Status: Active frontend canon overlay
Installed: 2026-05-16
Authority: Subordinate to `docs/truth/*` and the Frontend Authority Index; authoritative for chrome enrichment direction where compatible with active truth and live source.
Implementation claim: Docs-only. This doctrine does not prove SwiftUI implementation, simulator/device parity, screenshot parity, accessibility conformance, performance, release readiness, or shipped behavior.

## Purpose

This doctrine enriches Ambitions chrome to the quality tier of the best downloaded native iPhone apps without copying their visual identity. In this document, chrome means the persistent and semi-persistent interface shell around Ambitions content: top context edges, tab bars, composers, CTAs, rails, receipt handles, sheets, trays, continuity strips, source/proof affordances, gestures, and safe-area behavior.

Ambitions chrome must make the product feel like a private local-first life operating system, not a generic productivity app. The shell should continuously answer:

1. What state am I in?
2. What object owns this surface?
3. What action matters now?
4. What changed?
5. What proof or reasoning can I inspect?
6. How can I adapt without losing place?

## North Star Formula

`Persistent Reality Context + One Privileged Action + Local Proof + Contextual Overlays`

Translated into Ambitions:

- Persistent Reality Context: Reality Meridian, compact context edge, capacity, protected/free/work/school/away state, current-time marker, active step state.
- One Privileged Action: Start here, Start now, Open step, Capture composer, Adjust plan, Close loop, Place this.
- Local Proof: receipt handle, why-this drawer, source-quality line, proof attachment, local-only trust cue, replay-after-relaunch evidence.
- Contextual Overlays: Step Detail, Closure Sheet, Recovery Sheet, Adjust Plan Sheet, Receipt Drawer, Proof Sheet, Schedule Conflict Sheet.

## Authority Contract

This doctrine is an enrichment overlay. It does not replace existing recipes for Global App Shell, Today, Goals, Capture, Time, or You. It tightens their chrome expectations and resolves ambiguous shell decisions toward the following defaults:

- object-first surfaces, not dashboards
- bottom-reachable primary actions
- compact contextual top chrome, not thick page headers
- visible state, not hidden intelligence
- inspectable local proof, not vague AI confidence language
- contextual sheets, not disconnected modals
- one dominant object per top-level destination
- active IA exactly `Today / Goals / Capture / Time / You`

If older frontend language conflicts with this doctrine and is not higher authority, prefer the chrome pattern that preserves the dominant object, the current reality state, and the local proof trail.

## Market-Derived Chrome Patterns To Abstract

Ambitions should learn structurally from top-tier app chrome without copying their designs:

- Maps and ride/delivery apps preserve orientation while action controls float or sheet over the primary object.
- Media apps preserve active session continuity while the user browses elsewhere.
- AI assistants use one universal composer, but Ambitions must embed local intelligence into decisions instead of making chat the top-level destination.
- Messaging and email apps keep triage and thread state visible without turning every action into a dashboard.
- Finance and commerce apps make transaction or trust state explicit with receipts, confirmations, and status indicators.

The Ambitions translation is a local execution shell: the user always sees time reality, next action, adaptation path, and proof.

## Global Living Chrome

Global chrome must be shared enough that Ambitions feels like one product, but flexible enough that each destination keeps its dominant object.

### Required global ingredients

- Compact top context edge for current destination, local state, and origin when needed.
- Premium bottom tab bar with exactly `Today / Goals / Capture / Time / You`.
- Contextual sheet system for inspection, closure, recovery, adjustment, conflict, and proof.
- Receipt micro-layer attached to the object or state it explains.
- Continuity strip only when an active execution, closure, recovery, reflow, or proof state needs to persist across surfaces.
- Thumb-zone ownership for primary actions.
- Safe-area-aware composition that respects one-handed iPhone use.

### Required global behavior

- Do not let the shell compete with the surface object.
- Do not introduce an AI/chatbot destination.
- Do not use equal-weight card stacks as the primary orientation pattern.
- Do not hide mutations. Any meaningful local adaptation needs a receipt, undo, or explicit no-receipt reason.
- Do not use color, glow, or motion as the only state carrier.

## Today Flagship Chrome

Today is the proof surface for Ambitions chrome quality.

Required Today chrome:

- Reality Meridian is the primary object, not a decoration.
- Scheduled nodes and the live current-time glow are separate objects.
- The live current-time glow sits at the exact current time, even when the plan has drifted.
- Start Here is physically related to the Meridian and never reads as a generic recommendation card.
- Start Here includes recommended step, why now, goal thread, time fit, local receipt cue, primary action, and adjustment path.
- Prior unresolved steps appear as soft closure prompts, not shameful overdue items.
- Compact `Local · Ambitions` identity may appear where it anchors trust without becoming marketing chrome.
- Proof/recovery remains sparse at rest and inspectable on demand.

Today fails the chrome gate if it reads as a task list, dashboard, motivational page, generic calendar, or chatbot recommendation feed.

## Goals Chrome

Goals must feel like a strategic intent layer, not project management.

Required Goals chrome:

- Constellation Atlas owns the root surface.
- Goal thread rail links intent to plan to step to proof.
- Goal Detail remains one destination with lane-based Mission Control.
- Momentum, proof, blocked/recovery states, and next recommended step are visible without turning into a board clone.
- Lane drill-downs preserve origin and proof continuity.

## Capture Chrome

Capture should be Ambitions' universal intent intake surface, not a notes list and not a chatbot.

Required Capture chrome:

- Atmosphere Composer is the primary visible object.
- Bottom composer owns text input; mic lives inside the field; add action sits to the right.
- Main Capture surface avoids normal scrolling.
- First-use state reveals routes only after input.
- Post-capture routes use Ambitions language: Needs a Place, Ready to Place, Grow into Goal.
- Dark-sky/starfield signature is restrained and limited to Capture and First Run.

## Time Chrome

Time must be LifeShape Field, not a generic calendar clone.

Required Time chrome:

- Scope chip supports Day / Week / Month.
- Day view shows scheduled items, free time, protected blocks, pressure, capacity, and evidence labels.
- Week view emphasizes pressure distribution, recovery risk, goal load, and availability windows.
- Month view is LifeShape, not a generic grid; it emphasizes life areas, pressure weeks, milestones, protected time, and capacity trends.
- Reflow and conflict overlays explain what changed before asking the user to accept it.

## You Chrome

You must feel like iOS Settings crossed with a private operating profile.

Required You chrome:

- UserSystemProfilePanel sits at the top.
- Planning Setup is high in the hierarchy.
- Grouped navigation rows remain compact, native, and explicit.
- Trust controls expose what Ambitions uses, what it does not use, what stays local, and how receipts can be inspected.
- Default automation level is Guided unless active truth changes that rule.

## Local Intelligence Chrome

Local intelligence is not a destination. It appears through decisions, receipts, and adaptation.

Allowed surfaces:

- Start Here reasoning
- Receipt Drawer
- source-quality line
- local proof chip
- suggested reflow
- closure and recovery prompts
- schedule conflict explanation
- goal-to-step decomposition proof
- capture triage
- replay-after-relaunch evidence

Forbidden surfaces:

- AI tab
- chatbot-first home
- generic assistant feed
- model confidence score as user-facing truth
- hidden cloud dependency for core behavior
- ornamental local-first claim without proof

## Motion and Haptic Contract

Motion clarifies relationship, origin, before/after, confirmation, and recovery. It must never be the only carrier of meaning.

Required motion patterns:

- Start Here expands by revealing proof/recovery context, not by becoming theatrical.
- Receipt Drawer opens as a short bottom sheet or object-attached reveal.
- Exact-time Meridian motion is subtle and truthful to current time.
- Plan reflow uses before/after preview before commit.
- Capture routing feels like the captured object moving into a destination.
- Reduce Motion replaces movement with labels, fades, static attachment, and explicit state summaries.

Haptics are limited to light selection, closure confirmation, primary Start now confirmation, and hard-conflict boundary feedback.

## Accessibility Contract

Every chrome primitive must pass these gates:

1. VoiceOver order matches visual hierarchy.
2. Current-time marker has non-color indication.
3. Receipt and proof affordances have explicit labels.
4. Closure states are understandable without color.
5. Dynamic Type preserves dominant object, primary action, receipt path, and cancel/recovery path.
6. Reduced Motion preserves all state meaning.
7. Tap targets meet native iPhone comfort.
8. Sheets preserve focus and dismiss predictably.
9. Local/privacy states are not icon-only.
10. No surface requires the user to infer state from glow, animation, or celestial decoration.

## Anti-Patterns

Ambitions chrome must not drift into:

- dashboard shell
- productivity card stack
- generic task app
- generic calendar clone
- chatbot-first app
- deal/commerce urgency chrome
- motivational coaching wallpaper
- score/streak/gamification shell
- hidden mutation engine
- decorative celestial layer with no state meaning
- thick headers that waste vertical space
- ungrounded AI explanation copy

## Implementation Gate

Chrome enrichment should proceed in this order:

1. Audit current chrome and classify active/supporting/historical/obsolete material.
2. Bind this doctrine to the Frontend Authority Index and visual encyclopedia.
3. Install primitive-level recipes.
4. Install Today chrome first.
5. Extend the shared chrome grammar across Goals, Capture, Time, and You.
6. Add trust/proof/local-first chrome.
7. Validate visual, accessibility, motion, terminology, source-binding, and release-honesty gates.

No SwiftUI implementation is authorized by this document alone. Implementation must go through the Ambitions runner, active source packets, allowed scope, proof expectations, and rollback instructions.
