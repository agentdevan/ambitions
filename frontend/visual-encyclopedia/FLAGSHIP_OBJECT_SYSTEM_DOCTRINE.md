# Ambitions Flagship Object System Doctrine

Status: Active frontend canon overlay
Installed: 2026-05-16
Authority: Subordinate to `docs/truth/*` and `frontend/visual-encyclopedia/FRONTEND_AUTHORITY_INDEX.md`; authoritative for flagship-object design, object graph expectations, object proof, and Codex implementation sequencing where compatible.
Implementation claim: Docs-only. This doctrine does not prove SwiftUI implementation, simulator/device behavior, screenshot parity, accessibility conformance, performance, App Store readiness, award readiness, or shipped behavior.

## Purpose

This doctrine defines the target system for making every Ambitions object flagship quality: semantic, stateful, adaptive, inspectable, animated with purpose, accessible, local-first, proof-backed, native iPhone-first, visually impressive, and production-grade.

Ambitions must not become a set of beautiful screens. It must become an object operating system. Every visible object should carry life reality, local intelligence, user control, and proof. The app should feel like a trendsetting native iPhone product because the objects themselves are alive, coherent, and meaningful.

## Flagship Object Definition

A Flagship Object is a semantic product unit that has:

1. stable identity
2. product role
3. anatomy zones
4. state machine
5. local reality context
6. source/proof/receipt behavior
7. primary and secondary user actions
8. motion and haptic contract
9. accessibility contract
10. preview scenario matrix
11. implementation receipt
12. visual proof
13. rollback path

A view is not a Flagship Object until it has the model, state, proof, motion, accessibility, preview, and test contracts that let Ambitions reason about it.

## North Star

Ambitions should operate as:

`Truth -> Surface Universe -> Object Graph -> Object Kernel -> State Machine -> Motion/Accessibility Contract -> SwiftUI Renderer -> Preview Matrix -> Proof Receipt -> Validation Gate`

The product should feel like:

- a private local-first life runtime
- a native iPhone execution OS
- a living temporal system
- a proof-backed recommendation and recovery engine
- a visually original object language
- a calm, high-production-value, world-class app

## Award-Level Design Target

The design target is not merely visual polish. Ambitions should be built toward the same qualities rewarded by world-class iOS products:

- distinctive interaction grammar
- platform-native control behavior
- inclusive accessibility from the object level
- high-quality motion that clarifies state
- original visual system that could be recognized label-off
- meaningful impact through shame-free recovery and user agency
- technical craft visible in edge cases, not only happy-path screens

No document may claim Ambitions is award-ready until implementation proof, visual proof, accessibility proof, performance proof, and release proof exist.

## Product Moat Relationship

The Flagship Object System is a moat execution layer. It exists to make the Private Life Runtime visible and trustworthy.

The moat is not a generic goal/task UI. The moat is:

- intent becomes personalized daily execution
- the same intent becomes different daily plans for different users
- planning adapts locally as reality changes
- closure and recovery preserve dignity
- proof and receipts make the system inspectable
- local-first intelligence becomes visible through object behavior

Objects are where that moat becomes felt.

## Object Quality Bar

Every Flagship Object must satisfy:

| Quality | Required Meaning |
| --- | --- |
| Semantic | The object represents an Ambitions concept, not a generic card. |
| Stateful | It has explicit states and allowed transitions. |
| Adaptive | It reacts to time, capacity, proof, source, closure, recovery, or user context. |
| Inspectable | It exposes why, source, proof, receipt, or no-receipt reason. |
| User-owned | It previews meaningful change and offers cancel/undo/recovery where relevant. |
| Beautiful | It uses Ambitions materials, rhythm, hierarchy, and visual signature with restraint. |
| Native | It respects iPhone reach, safe areas, gestures, Dynamic Type, and platform conventions. |
| Accessible | It works with VoiceOver, Dynamic Type, Reduce Motion, Increase Contrast, Reduce Transparency, and Differentiate Without Color. |
| Animated | Motion communicates origin, continuity, state change, or confirmation. |
| Proven | It has previews, tests, screenshot/preview proof, implementation receipt, and known gaps. |

## Object Anatomy Contract

Every object must define these zones:

1. Object Identity Zone
2. Dominant State Zone
3. Local Context Zone
4. Action Zone
5. Source / Proof / Receipt Seam
6. Recovery / Undo / Correction Zone
7. Accessibility Summary Zone
8. Motion/Transition Zone

At rest, the object must expose one dominant meaning and one dominant action or inspection path. Secondary metadata collapses before identity, state, proof seam, or recovery path.

## Object Graph Contract

Objects do not float independently. Every object must live in a graph.

Required graph edges:

- object -> destination
- object -> surface recipe
- object -> source binding
- object -> domain model
- object -> state machine
- object -> proof/receipt behavior
- object -> motion contract
- object -> accessibility contract
- object -> preview scenarios
- object -> tests
- object -> implementation receipt

The graph must allow reviewers and Codex to answer:

- What object is this?
- Which surface owns it?
- Which source files implement it?
- Which states are supported?
- Which transitions are allowed?
- Which proof is required?
- Which previews and tests prove it?
- Which gaps remain?

## Code Architecture Contract

SwiftUI view files must not invent object semantics. The hierarchy is:

`Runtime data -> Object Kernel -> State Machine -> View Model -> SwiftUI Renderer -> Preview/Proof`

Required Swift layers:

1. Object identity and graph models
2. Object-specific kernels
3. State machines
4. Motion contracts
5. Accessibility contracts
6. Preview scenario matrices
7. Renderer components
8. Tests and validation gates

Shallow display structs such as `title`, `subtitle`, `icon`, and `color` are insufficient unless wrapped in a semantic object kernel with state, proof, action, motion, accessibility, and preview behavior.

## Visual Production Value Contract

Every flagship object must carry Ambitions' visual language:

- graphite operating ground
- quiet luxury depth
- restrained celestial orientation where semantically allowed
- local proof seams
- luminous trace for continuity, time, source, or relationship
- native iPhone typography and spacing
- progressive disclosure
- beautiful empty/blocked/waiting/recovery states
- label-off recognition
- no generic productivity card stacks
- no chatbot-first framing
- no calendar clone Time
- no settings clone You

Beauty must come from meaning, not decoration.

## Motion Contract

Every object transition must map to a purpose:

- orientation
- selection
- confirmation
- correction
- recovery
- source check
- proof reveal
- reflow preview
- local-only settle

Every motion must have:

- motion token
- transition reason
- non-motion fallback
- haptic boundary
- accessibility summary
- testable state outcome

Motion must never be the only meaning carrier.

## Accessibility Contract

Every object must ship with:

- VoiceOver summary
- VoiceOver order
- custom actions where needed
- Dynamic Type layout behavior
- Reduce Motion equivalent
- Reduce Transparency equivalent
- Increase Contrast behavior
- Differentiate Without Color behavior
- minimum touch target proof
- cognitive-load/ADHD safety behavior

If an object is visually impressive but inaccessible, it is not flagship quality.

## Proof Contract

Every flagship object must have proof before it can be called implemented:

- scenario previews
- visual proof or screenshots
- Dynamic Type proof
- Reduce Motion proof
- VoiceOver proof
- interaction proof
- source/proof/receipt proof
- tests run
- drift check
- implementation receipt
- known gaps
- rollback notes

If proof is absent, readiness is absent.

## Codex Contract

Codex must not be asked to merely build screens. Codex must install semantic objects.

Required Codex instruction pattern:

`Install <object> as a semantic, stateful, accessible, animated, proof-backed product unit with object kernel, state machine, renderer, preview matrix, tests, source binding, and implementation receipt.`

Codex must stop red if it would:

- create a shallow component without object kernel
- add visual polish without state/proof/accessibility
- create a one-off view that bypasses the object graph
- hide a local adaptation without receipt/undo/proof
- use color, glow, or motion as the only state carrier
- use generic productivity/card-grid/calendar/chat/settings patterns
- claim release or award readiness without proof

## Required Implementation Sequence

1. Install object graph authority and matrices.
2. Install Swift object identity/core contracts.
3. Install object-specific kernels for primary and cross-surface objects.
4. Install state machines and transition tables.
5. Install motion/accessibility contracts.
6. Install preview scenario matrix.
7. Bind source files and proof receipts.
8. Implement Today flagship objects first.
9. Extend shared receipt/closure/proof objects.
10. Implement Capture, Time, Goals, and You objects.
11. Run object proof matrix and anti-generic gates.
12. Produce design-award-readiness audit without making award claims.

## Non-Claims

This doctrine installs the target system and plan. It does not implement the system in Swift. It does not prove the app is visually complete, accessible, performant, release-ready, or award-ready.
