# Ambitions Native Visual Foundry

Produce one honest native visual iteration. Orchestrate the repository canon,
SwiftUI preview, simulator, debugger, TDD, and verification workflows; do not
repeat their full instructions here.

## Before editing

1. Read only the relevant canon and installed VC authority. Treat legacy views
   and Figma as reference, never visual authority.
2. Resolve the primary semantic object and its canonical owner.
3. Name the native Apple behavior that remains default.
4. Select exactly one synthetic fixture and one viewport.
5. Render the current native state. Record protected characteristics before
   proposing a change. If no prior frame exists, say so.

## During editing

- Change one viewport, posture, or interaction only.
- Use production-intended SwiftUI behind a fixture adapter; keep runtime
  adapters replaceable and disconnected.
- Preserve system typography, natural scrolling, native controls, safe areas,
  and accessibility semantics.
- Do not invent runtime capability or imply that fixture state proves runtime
  behavior. Do not copy legacy view code or make unrelated refinements.
- Use Liquid Glass guidance only for functional crown or dock chrome, always
  with an authored opaque Reduce Transparency equivalent.

## After editing

Rebuild or hot reload. Verify that a real native frame rendered; a loaded
preview page is insufficient. Capture screenshot evidence, compare before and
after when a prior frame exists, and run lightweight changed-scope validation.

Report these headings exactly:

1. Preserve exactly
2. Changed
3. Removed
4. Added
5. Unresolved
6. Architecture-sensitive assumptions
7. Validation
8. Evidence
9. Proof ceiling

Identify the fixture ID, viewport, device/OS, appearance, Dynamic Type size,
accessibility settings, commands/tools, results, and screenshot paths. Mark
fixture copy as non-canon and evaluation screenshots as non-production
baselines.

## Escalate to full-app verification

Preview proof is insufficient when navigation, dock behavior, Search or Capture
presentation, keyboard or safe-area behavior, focus or restoration, sheets or
consequential review, runtime data, or a viewport proposed for owner closure
changes. Verify those cases in the full app without widening implementation
scope. If the live app is intentionally disconnected, report the escalation as
unresolved rather than manufacturing proof.
