# PLOS Risk Register

Status: Active readiness-control risk register
Updated: 2026-06-12

| Risk | Class | Why it matters | Gate / mitigation | Current status |
|---|---|---|---|---|
| Synthetic issue drift | Red | PLOS labels can look like issue identifiers but Linear writes require real `AMB-*` IDs. | `PLOS_LINEAR_ISSUE_MAP.json`, `plos-readiness-validate.py`, closeout validator, Red stop for PLOS label writes. | Controlled for phase parents; child labels must live-resolve before use. |
| False Green | Red | Governance or heading checks can pass while runtime, privacy, safety, or owner proof is absent. | Expanded phase gates, reviewer prompts, closeout fields, explicit proof boundary in run-state. | Controlled for readiness; runtime proof still future. |
| Phase-order violation | Red | Later runtime work can invalidate foundations if M00/M01/M10 gates are bypassed. | Strict `M00..M26` queue and phase-gate validator. | Controlled by queue; M00 is in progress under AMB-608 only and M01+ remains blocked. |
| Runtime implementation during readiness hardening | Red | The current task is control-plane hardening only. | Allowed path scope excludes app source and project files; preflight blocks dirty source paths. | Controlled in current run. |
| Private user data in R2 | Red | Source Atlas may use public reference distribution, not user-private data storage. | Source Atlas hardening plan, R2 boundary standard, Source Atlas validator. | Controlled as policy; future implementation must prove. |
| Required cloud LLM/core server drift | Red | Ambitions core intelligence must remain local-first and inspectable. | Truth-file authority, PLOS red gates, reviewer prompts. | Controlled as policy; future implementation must prove. |
| Source Atlas duplicate architecture | Yellow/Red | New pack tooling could bypass existing Source Atlas scripts, receipts, or rollback paths. | Source Atlas Factory hardening plan and validator require reuse, source binding, release receipt, rollback. | Yellow until future source mapping is completed under M01/M04/M05/M06. |
| Child issue map incompleteness | Yellow | Phase parent map is complete, but a future child run can still drift if it uses a PLOS child label directly. | Child execution requires live Linear resolution to `AMB-*` and run-state recording before work. | Yellow by design; fail-closed at child execution. |
| Parallel governance OS | Red | AMB-608 must extend existing truth, Goal Mode, Codex OS, PLOS, Source Atlas, validation, and proof-ledger systems instead of creating a second operating system. | AMB-636 governance inventory and do-not-duplicate list. | Controlled for AMB-636; future M00 children must extend named owners. |
| Personal Life OS law drift | Red | A supporting PLOS law could accidentally override truth files or claim runtime implementation. | `docs/codex/PERSONAL_LIFE_OS_RUNTIME_LAW.md` is subordinate to `docs/truth/*`, declares non-claims, and is wired into M00 gates only as governance authority. | Controlled for AMB-637; future PLOS issues must cite it without overclaiming implementation. |
| Any-goal false certainty | Red | The "any goal" promise can drift into fake full pathing, hardcoded private Steps, unsafe local drafts, or private goal leakage through coverage requests. | `docs/codex/ANY_GOAL_SOLUTION_LOOP_LAW.md` requires explicit operating modes, coverage-demand privacy boundaries, reusable seed gaps, and guarded/blocked high-risk routing. | Controlled for AMB-638 as governance law; implementation proof remains future. |
| Source Atlas static-library drift | Red | Source Atlas could be treated as passive content instead of source authority for freshness, revocation, contradiction, jurisdiction, risk, review, runtime eligibility, and share eligibility. | `docs/codex/SOURCE_ATLAS_AUTHORITY_LAW.md` requires internal source states, compressed user-facing states, applicability envelopes, and eligible-state-only Recommended step/schedule install. | Controlled for AMB-639 as governance law; source freshness/runtime proof remains future. |
| Hardcoded Step pack drift | Red | Source packs could become exact-user finished Step stores, causing synthetic issue drift, privacy leakage, generic planning, and false source truth. | `docs/codex/SEED_BASED_PLANNING_LAW.md` requires reusable seed taxonomy, runtime composition, Step Quality Firewall integration, and a hardcoded-Step prohibition except local-only user mini-pack value models. | Controlled for AMB-639 as governance law; seed implementation proof remains future. |
| Rigid Step drift | Red | Steps could be treated as fixed tasks, causing shame, false failure, proof loss, replacement-only adaptation, hidden goal cannibalization, or Step Elasticity as surface-level UI. | `docs/codex/STEP_ELASTICITY_RUNTIME_LAW.md` requires required Step forms, top-level and advanced controls, runtime-relevant Vibe Signature, mutation impact calculations, Step Quality Firewall, and Life Consequence Reflow linkage. | Controlled for AMB-640 as governance law; Step Elasticity Engine and reflow proof remain future. |
| Silent reflow harm | Red | Step, path, source, schedule, or goal changes could silently damage another active goal, break protected time, erase proof value, or make a deadline impossible. | `docs/codex/LIFE_CONSEQUENCE_REFLOW_LAW.md` requires reflow triggers, build tiers, severity tiers, non-suppressible events, Goal Treaty, receipt/failure state, and blocks Quiet mode from hiding material harm. | Controlled for AMB-641 as governance law; reflow engine and schedule install proof remain future. |
| Trust-light opacity | Red | Quiet UI could become opaque, hide source/receipt/consequence state, or replace trust with unlabeled glyphs, AI badges, dashboards, or false calm. | `docs/codex/TRUST_UI_DISCLOSURE_LAW.md` requires disclosure layers, source-state compression without lying, glyph/breadcrumb rules, no false calm, and future visual/accessibility proof for UI claims. | Controlled for AMB-642 as governance law; UI implementation and screenshot/accessibility proof remain future. |
| Cognitive-load drift | Red | PLOS UI could become paragraph-heavy, dashboard-like, shame/scoring driven, hard to parse under attention strain, or inaccessible while claiming Green. | `docs/codex/ADHD_COGNITIVE_LOAD_UI_LAW.md` requires one-primary-object/action discipline, density rules, copy constraints, progressive disclosure, and explicit accessibility-proof boundaries. | Controlled for AMB-642 as governance law; low cognitive-load UI implementation proof remains future. |
| Child closeout validator gap | Yellow | Project-level PLOS closeout validation could block or distort child issue closeout. | Extend `scripts/codex/linear-closeout-validate.py` with child/phase scope instead of adding a new validator. | Repaired in AMB-636; AMB-645 may refine reporting templates. |
| Context churn across compaction | Yellow | Long PLOS execution can lose phase, issue, validation, and proof state. | Expanded run-state, execution queue, closeout template, validator support. | Controlled for current handoff. |
| Release/readiness overclaim | Red | Local simulator or docs proof is not release proof. | Release truth, closeout validator, audit proof boundary. | Controlled by closeout requirements. |
| Validator blind spot | Yellow | Validators can check structure, not product truth or visual/runtime behavior. | Reviewer prompts and focused validation remain mandatory for source-changing phases. | Yellow; owned by phase-specific execution. |
