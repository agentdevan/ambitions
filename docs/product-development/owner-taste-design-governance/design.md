# Design — Owner Taste Design Governance

The durable source is `docs/canon/design/OWNER_TASTE_DESIGN_DECISION_SYSTEM.md`
with its JSON peer. That pair declares `supreme_design_authority`, an exact
design precedence beginning with `owner_taste`, an exact conflict rule, and a
separate non-design constraint boundary. The VC input contract carries an
`owner_taste_authority` binding and an `implementation_calibration` payload.
Its selected direction IDs remain useful working targets but are explicitly
subordinate and cannot narrow or override Owner Taste.

The compiler rejects a subordinate Owner Taste status, any VC claim to be the
active controller, missing or stale human/machine links, a non-iPhone scope,
invalid precedence or constraints, undeclared dispositions, and missing
accessibility or physical-haptic evidence obligations. The generated visual
manifest exposes `supreme_design_authority` separately from
`implementation_calibration` and labels every projected VC direction as an
owner-taste-subordinate calibration.

Frontend impact: affected — this changes decision routing for future material
iPhone-native work, but creates no product UI. Visual gate: not required for
this documentation/governance change. A future candidate uses the 12-dimension
0–2 gate before expensive proof; the score cannot approve a design or certify
behavior, accessibility, runtime, device, or release proof. Physical-iPhone
validation is required for physical realization. Evidence can invalidate an
implementation or proof claim; Owner Taste still controls design intent,
including haptic character.
