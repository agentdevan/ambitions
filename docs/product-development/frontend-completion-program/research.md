## Idea and user problem

Ambitions needs one completion program for its frontend rather than parallel
calibration campaigns, partial component-library work, and a production app
whose UI still belongs to a legacy implementation. The user-facing problem is
not a lack of individual attractive screens. It is that a local-first product
cannot feel coherent, trustworthy, or complete until every root and global
journey shares one Apple-native system, carries truthful runtime state, and
removes the superseded frontend authority.

The program is named **Ambitions Unified Maximum Polish Frontend Program**
(UFP). Its outcome is a single production frontend rather than a Foundry
prototype, a parallel presentation package, and retained legacy presentation
all claiming a portion of the experience.

## Current truth

The owner-approved design authority is Owner Taste. It requires contextual
richness with native discipline, integrated composition instead of generic card
stacks, information-led hierarchy, restrained materials, and motion that
explains continuity or state. It also makes privacy, accessibility, correct
object semantics, and Apple platform behavior hard boundaries.

`RECONCILED_FLAGSHIP_RECONSTRUCTION_PLAN.md` records the older FR-1 through
FR-7 sequence and correctly separates Foundry fixture proof from production
authority. This UFP packet absorbs that separation into a complete program:
Foundry remains a fixture, render, and proof environment only. It is never a
production source owner or a substitute for runtime, device, accessibility, or
release proof.

The current `AmbitionsPresentation` package has four products/targets:
`AmbitionsPresentationContracts`, `AmbitionsFlagshipFoundation`,
`AmbitionsFlagshipUI`, and `AmbitionsNativeVisualFoundry`. The first three
already suggest the intended canonical module roles—Contracts, Foundation, and
UI—while the Foundry target is independently hosted by
`AmbitionsNativeFoundryHost`. The production app currently declares all three
non-Foundry presentation products, but its production source contains a broad
legacy frontend spread across `Native/Ambitions/DesignSystem`, `Stage`,
`Rendering`, `Surfaces`, `Composer`, and related support. Neither existence nor
an existing package dependency establishes that a component is promotable.

The operational program ledger is the sole file at
`/Users/devan/.codex/output/Ambitions_Maximum_Polish_Program/PROGRAM.json`.
It is outside this repository and is upgraded in place by the integration lane.
Repository lifecycle and canon documents provide durable governance; they are
not a shadow program ledger.

## Evidence

- Owner Taste explicitly ranks design authority above Visual Closure and
  historical provenance, rejects sparse-premium/card-stack/dashboard defaults,
  and requires native behavior plus authored composition.
- The reconciled plan requires fixture-to-production separation, a real Today
  vertical slice before broad reconstruction, parity/rollback before deletion,
  and physical-device validation before release claims.
- Component-sourcing research supports an Apple-native behavioral substrate:
  SwiftUI controls, navigation, sheets, focus, system accessibility, Charts,
  and supported animation APIs; Ambitions should author semantic composition
  only where product meaning recurs. It rejects general UI kits, custom
  navigation frameworks, universal shimmer, third-party charts, and animation
  runtimes as default dependencies.
- The presentation package boundaries prove a useful starting separation but
  do not prove final module APIs, runtime integration, or an approved visual
  system.
- Current decision chronology records Today R04 D-129 as approved and locks
  the next active calibration focus to Time. That decision is program input,
  not a production cutover authorization.

## Alternatives

### Continue root-by-root Foundry work

This preserves rapid fixture exploration but leaves production integration and
legacy deletion indefinitely deferred. It cannot yield a single frontend
authority.

### Promote current presentation components opportunistically

This is faster at first, but freezes overlapping APIs because they already
exist. It conflicts with the component-sourcing conclusion that shared
abstraction must follow shared semantics, state, accessibility, and lifecycle.

### Adopt a general third-party UI system

This adds another visual language, supply-chain surface, and removal problem
without resolving Ambitions' object semantics. It is not the default.

### Complete a fixture-approved system, then reconstruct production and delete legacy

This preserves Foundry as evidence, earns promotion/rebuild choices from a
complete component census, and makes final deletion measurable. It best meets
the local-first, native, and owner-taste constraints.

## Unknowns and risks

- Exact production owners, legacy file boundaries, and dependency edges must
  be inventoried from the final bytes before UFP-6; no approximation can
  authorize deletion.
- Owner visual approval is required for the complete fixture-driven frontend
  and design system before any production wiring. A passing fixture suite is
  not that approval.
- Current fixture data is synthetic. Production adapters must preserve local
  persistence, replay, idempotency, restoration, Receipt, and recovery truth.
- UFP must avoid freezing a component family because it looks shared. Every
  in-scope component needs an explicit UFP-4 disposition.
- Physical-device differences (OLED, keyboard, reach, system gestures,
  haptics, scrolling, and VoiceOver) can invalidate a candidate despite
  simulator or Foundry proof.

## Frontend impact investigation

- Potential frontend impact: certain
- Existing surfaces investigated: Today, Goals, Time, You, Search, Capture,
  shell/navigation, contextual receipts and recovery, the app's legacy
  `Native/Ambitions` frontend, `Packages/AmbitionsPresentation`, and the
  Native Foundry host.
- Evidence and unknowns: the work changes surface ownership, navigation,
  component families, visual language, motion, accessibility, and asset
  ownership across every product-facing route. The exact legacy inventory and
  final canonical UI API remain intentionally uncommitted until UFP-4,
  canonical fixture source completion at UFP-5, and complete fixture-driven
  owner approval.

## Recommended direction

Run one UFP sequence, UFP-0 through UFP-8, with the outside-repository
`PROGRAM.json` as its sole operational ledger. Use Apple-native behavior by
default; allow Ambitions-owned semantic composition only when its recurring
product meaning earns ownership; require a documented exception and exit plan
for any third-party UI dependency. Keep Native Foundry fixture-only. Do not
wire production to the new frontend until complete fixture-driven
frontend/design-system owner approval is recorded. Then build production in
the canonical **Contracts → Foundation → UI** module direction, prove each
vertical slice against real local runtime state, and end with deletion of every
legacy frontend file, dependency, target, asset, and wrapper with no unused
legacy remaining.
