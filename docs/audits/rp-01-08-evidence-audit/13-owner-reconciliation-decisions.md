# 2. Locked Devan decisions

The audit listed ten unresolved owner decisions. They are resolved as follows.

## D-DEV-01 — Crowned Edge Dock versus bottom-navigation canon

**LOCKED DECISION**

The **Crowned Edge Dock remains the target flagship shell**.

The current bottom-navigation canon and source must be revised through architecture and UX reconciliation rather than treated as future visual authority.

Conditions:

- Native root-selection semantics must remain available to accessibility and system behavior.
- Each root must retain an independently owned path.
- Back gestures and system-edge gestures must remain correct.
- Root/global ownership must remain explicit.
- Search and Capture remain non-root global capabilities.
- Hidden, Peek, Expanded, mirrored, labelled, opaque, keyboard-aware, and lower-reach states require one authoritative shell owner.
- The existing bottom rail remains only until the reconstructed shell reaches parity and cutover proof.
- If architecture proves the edge dock cannot satisfy native, accessibility, restoration, and gesture requirements, return to Devan with a new shell branch. Do not silently fall back to bottom tabs.

**Direction treatment:** Preserve `AVF-SHELL-S07-R00`; create reconciliation revision `AVF-SHELL-S07-R01`.

## D-DEV-02 — Goal-led versus Life-Area-led Goals root

**LOCKED DECISION**

The Goals root is **Life-Area-led**.

The Linked Goal Lens survives inside the selected Life Area and Goal-owned depth.

### New structural branch

**AVF-GOALS-S08-R00 — Life Area Linked Goal Lens**

Protected formula:

> Editable Life Area index → selected Life Area goal field → inline Linked Goal Lens on goal selection → focused pursuit timeline → integrated settlement and history

Root hierarchy:

1. Living editable Life Area index
2. Selected Life Area depth
3. Goal identities within the Life Area
4. Inline Linked Goal Lens beneath the selected Goal
5. Focused continuous pursuit timeline

Preserved from `AVF-GOALS-S07-R01`:

- Goal identity before status
- Inline semantic lens
- Maximum one consequential relationship at the overview level
- Continuous pursuit progression
- Completed, active, planned distinction
- Integrated completion
- Structural conflict interruption
- Native exact-context return

Required architecture:

- Canonical stored `LifeAreaRecord`
- Stable Life Area identity
- Editable lifecycle
- Goal membership
- Migration from enum-derived values
- Search and projection identity

`AVF-GOALS-S07-R01` remains historical campaign authority but is superseded for the root structure by `AVF-GOALS-S08-R00`.

## D-DEV-03 — Today hierarchy

**LOCKED DECISION**

Today returns to one dominant canonical **Start Here** object.

A maximum-three equal-priority region is rejected after reconciliation.

### New structural branch

**AVF-TODAY-S10-R00 — Start Here Contextual Command**

Protected formula:

> One dominant Start Here projection → optional earned Also Fits Now projection → consequential Today timeline → focused execution and owner handoff → explicit preview and truthful settlement

Root hierarchy:

1. Compact Today crown and date
2. **Start Here** — one dominant projected object
3. **Also Fits Now** — zero or one earned supporting projection
4. Today’s Timeline overview
5. See Full Day
6. Focused execution, interruption, conflict, and reshape depths

Rules:

- Start Here is a projection of a canonical object, normally a Goal Step or another explicitly supported owner object.
- It is not a new Today-owned canonical object.
- Also Fits Now appears only when eligibility and fit are grounded.
- The timeline remains supporting chronology.
- Today performs narrow contextual actions.
- Complex scheduling transfers to Time.
- Full goal editing transfers to Goals.
- Capture remains dock-owned.

`AVF-TODAY-S09-R00` remains historical campaign authority but is superseded for first-viewport hierarchy by `AVF-TODAY-S10-R00`.

## D-DEV-04 — Today priority identity

**LOCKED DECISION**

A Today priority is a **day-specific projection or admission relation**, not a duplicate canonical object.

It retains:

- Source object ID
- Owning root
- Why it appears today
- Current-day consequence
- Local available action
- Route to the owner

If manual pinning or explicit person-selected priority is later approved, model it as a typed relation/state against the canonical object rather than a copied object.

## D-DEV-05 — Time Week default

**LOCKED DECISION**

Week is the **first-use default**, not a forced reset rule.

After the person selects another supported Time view, restore the last-used view when the runtime can do so truthfully.

Until Day, Month, Year, and List reach parity:

- Week may be the only implemented flagship root scale.
- Unimplemented views must not appear selectable.
- The visual direction may retain the future scale family explicitly as planned.

**Direction treatment:** `AVF-TIME-S07-R01`.

---

## D-DEV-06 — Search Act experience

**LOCKED DECISION**

Search is not a mutation owner.

Search Act means:

1. Resolve a canonical object
2. Show supported current truth
3. Prepare the requested operation
4. Show consequence and uncertainty
5. Transfer to the owning context
6. Owner revalidates, confirms, commits, settles, and returns

The transfer may remain visually continuous, but authority is explicit.

Search may settle only non-mutating operations such as Open, Inspect, Compare, or Navigate.

**Direction treatment:** `AVF-SEARCH-D07-R01`.

---

## D-DEV-07 — Partial settlement

**LOCKED DECISION**

Partial settlement is required only for operations that genuinely contain independently settling scopes.

Until a typed per-scope settlement model exists:

- Do not show a Settlement Ledger.
- Do not present a cross-root operation as one multi-scope commit.
- Split the operation into atomic owner commits, or stop after preparation and owner handoff.
- Use whole-result changed, unchanged, blocked, failed, or unsupported outcomes.
- Preserve partial-settlement visual grammar as an architecture requirement, not current capability.

This retains the resilience principle without requiring every operation to become multi-scope.

---

## D-DEV-08 — Violet-indigo accent

**LOCKED DECISION**

Restrained violet-indigo becomes the default Ambitions action accent.

Migration policy:

- Add a restrained violet-indigo family to the canonical appearance model.
- Make it the default for new or reset appearance state.
- Existing persisted accents may remain selectable only if they pass light/dark, contrast, monochrome, and state-separation review.
- Accent never identifies roots.
- Accent never carries semantic state alone.
- Accent never creates glow.
- Existing values must migrate deterministically without corrupting saved preferences.

**Required durable meaning**

- Selected root

**Best effort only unless architecture explicitly persists it**

- Scroll position
- Editing cursor
- Field focus
- Keyboard visibility
- Transient animation state
- Exact pixel position

If a target is stale or missing, restore the deepest truthful surviving context and state what could not be restored.

# 6. Architecture decisions now required

## A. Shell and navigation

Create one authoritative shell/navigation state model owning:

- Selected root
- Root-local paths for all four roots
- Crown context
- Dock posture
- Active global presentation
- Selected-root-aware depth
- Restoration record
- Stale-target validation

Fix inactive-root route depth.

Define the native/custom boundary for:

- Back
- Toolbar
- Title
- Safe area
- Gestures
- Focus
- Root semantics

## B. Canonical identity

Implement or explicitly decline:

- `LifeAreaRecord`
- Canonical `EventRecord`
- Event series and occurrence identity
- `SchedulePlacementRecord`
- Goal/Step ID bridge rules
- Projection lineage
- Deletion/history behavior

Reconstruction must sequence identity migration before root rebuild.

## C. Truth-state algebra

Define a shared, capability-negotiated contract for:

- Current
- Proposed
- Accepted
- External
- Stale
- Unknown
- Saving
- Pending
- Settled
- Failed
- Conflict
- Irreversible
- Undo available

Domain-specific states may extend this only when ownership is explicit.

## D. Global action transfer

Create one owner-transfer envelope containing:

- Object identity
- Owning domain
- Source revision
- Originating context
- Requested action
- Preview
- Consequence
- Confirmation
- Commit result
- Receipt
- Undo availability
- Return target

Search and Capture use this envelope rather than becoming universal mutation owners.

## E. Receipts and settlement

Decide:

- Durable Receipt scope
- Receipt retention
- Object linkage
- Failure records
- Partial settlement architecture
- Settlement Ledger projection
- Per-scope reversibility
- Irreversible status

## F. Persistence and recovery

Define:

- Durable drafts
- Durable Search sessions if required
- Pending-operation owner
- Retry/backoff
- Cancellation
- Later result publication
- Notification
- Source priority
- Freshness
- Conflict resolution
- Restoration

Absent capabilities remain visually absent.

## G. You capability boundary

Define the current local-only product surface and remove duplicate/future authorities.

Only introduce accounts, continuity, sync, export, delete, or broad permissions through separate approved architecture.

## H. Accessibility and localization

Implement:

- Runtime accessibility focus owner
