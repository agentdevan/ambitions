## Purpose

EFC is the Flagship Proof Operating Layer for Ambitions. It upgrades the existing global batch train without creating a parallel product universe.

EFC exists because Ambitions does not reach a 100/100 flagship standard through more screens, more ceremonial docs, or broader product claims. Ambitions reaches 100/100 planned architecture when every product promise has an owner, implementation path, fixtures, tests, evidence, failure handling, trust controls, accessibility equivalence, privacy boundaries, and release-claim limits.

Core law:

```text
Every claim has an owner.
Every owner has a test.
Every test has evidence.
Every evidence gap blocks overclaiming.
Every user-impacting behavior has trust, privacy, recovery, correction, and release boundaries.
```

## Relationship To Existing Trains

EFC is not a replacement for AFI, FCP, PK, AOS, LDI, Source Atlas, PFC, FVQ, CQS, or REC.

Existing trains remain the implementation owners wherever they already own the work:

- AFI / FCP own flagship surfaces, object quality, visual language, and interaction execution.

EFC adds missing proof systems only where no current owner can produce the necessary flagship evidence.

## 100/100 Planned Architecture Standard

A batch that affects user-facing behavior, user data, intelligence, source/freshness, side effects, accessibility, release posture, or public claims cannot close Green unless it records the EFC proof slice that applies.

Required proof families:

1. Product proof — what user job is improved and how it is observed without surveillance.
2. Trust proof — source, why-this, receipt, correction, and user control are visible where relevant.
3. Privacy proof — sensitive data, logs, external surfaces, exports, and support paths are redacted by default.
4. Accessibility proof — nonvisual equivalent, VoiceOver order, Dynamic Type, Reduce Motion, Differentiate Without Color, and device proof where relevant.
5. Degraded-state proof — denied permissions, stale data, corrupt input, offline, no calendar, no source, manual mode, and empty state remain useful.
6. Test proof — focused unit/UI/fixture/visual/device/manual evidence appropriate to the batch type.
7. Release-claim boundary — what the batch proves and what it explicitly does not prove.
8. Recovery proof — user can adjust, reject, move, shrink, release, restore, or recover without shame where relevant.
9. Performance proof — budget, fixture, or explicit non-impact statement where rendering, runtime, side effects, or storage is touched.
10. Continuation proof — next eligible batch, blocked owners, and accepted Yellow caveats are recorded.

## Peak Sequencing Law

EFC sequencing is optimized as an overlay, not a hard serial wall across all work:

1. EFC00 is installed first as docs/governance proof wiring.
2. AFI12 and later UI-affecting work must inherit EFC accessibility-shadow and proof rules.
3. PK work must inherit EFC event/evidence/diagnostic/data-control requirements when touching platform safety.
4. AOS/LDI work must inherit EFC recommendation-court, language-benchmark, goal-thermodynamics, and twin-fixture rules when touching intelligence.
5. Source Atlas work must inherit EFC source-freshness operations when touching packs, claims, freshness, source review, importers, or mini-packs.
6. PFC/REC/FVQ release-facing work must inherit EFC real-device, release-truth, App Store creative, support, accessibility, and privacy proof rules.
7. EFC standalone batches run only where no current train owner can produce the proof.

## Hard Reds

Stop immediately if a batch:

- Treats EFC as approval to add a sixth tab or broad product surface.
- Treats EFC as approval for hosted AI, user-data server, cloud analytics, remote telemetry, or direct live API dependency for core behavior.
- Adds surveillance, productivity scoring, shame/streak mechanics, or hidden user profiling.
- Adds silent mutation without user review and receipt.
- Stores private raw content in diagnostics, support bundles, widgets, Live Activities, notifications, or logs without explicit user approval and redaction.
- Claims release, App Store, TestFlight, device, accessibility, privacy/legal, sync, or 100/100 product proof without matching evidence.
- Allows current active Codex batch state to be overwritten without checking `.codex/state/active-batch.yml` and the run-state files.
- Adds EFC as 30+ independent batches or broadens scope where an existing owner can absorb the proof.
