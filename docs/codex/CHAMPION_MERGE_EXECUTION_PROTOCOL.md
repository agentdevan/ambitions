# Champion Merge Execution Protocol

Status: Active Codex protocol  
Purpose: Consolidate duplicate/parallel Ambitions implementations into one best canonical implementation without losing stronger older code.

## 1. Purpose

Champion Merge turns audit findings into sequenced source work. It chooses canonical champions, rescues stronger fragments, wires runtime intelligence, proves behavior, and only then prepares weaker duplicates for quarantine or later deletion.

## 2. When Champion Merge Is Required

Champion Merge is required when any concept has duplicate implementation, weaker active implementation, stronger older/package/preview code, disconnected runtime wiring, more than one owner, no owner, or supersession without rescue decision.

## 3. Merge Principles

- Extend canonical owners.
- Do not create a new parallel implementation while merging.
- Keep changes source-truth grounded and reversible.
- Preserve current active product language.

## 4. Champion Selection Input Sources

- `EXISTING_PARALLEL_DAMAGE_ASSESSMENT.md` when present
- `CHAMPION_SELECTION_LEDGER.md`
- `BEST_CODE_RESCUE_LEDGER.md`
- `SUPERSESSION_LEDGER.md`
- `EXISTING_CODE_CHAMPION_COVERAGE.md`
- `PRIVATE_LIFE_RUNTIME_WIRING_MAP.md`
- `CANONICAL_OWNER_MAP.md`
- `docs/codex/canonical-owner-map.yml`
- `docs/codex/concept-lock-registry.yml`

## 5. Composite Champion Rule

The best result may combine the active app implementation for reachability, package primitives for visual quality, older runtime logic for state depth, older tests for edge coverage, newer receipt/replay services for trust, and accessibility helpers from another implementation.

Do not force one file to win if the best product requires a composite merge.

## 6. Rescue-Before-Retire Rule

No duplicate source can be retired until useful behavior is extracted, the champion owner is updated, tests prove rescued behavior, proof exists, rollback exists, and both supersession and best-code rescue ledgers are updated.

## 7. Runtime Wiring Rule

Any champion merge touching intelligence must wire through SourceRecord, Receipt, ReplayTrace, You / What Ambitions knows inspection, reset/delete controls, deterministic tests, proof artifacts, no cloud LLM dependency, no silent sensitive use, and no silent schedule mutation.

## 8. Accessibility Preservation Rule

Do not drop VoiceOver, Dynamic Type, Reduce Motion, Increase Contrast, non-color state, touch target, or preview fixture behavior when merging.

## 9. Performance Preservation Rule

Do not regress local latency, background work, recomputation, scrolling, launch, visual effect cost, or power posture without proof and owner acceptance.

## 10. Privacy / Local-First Preservation Rule

Champion Merge must preserve local-first deterministic behavior, user inspection, reset/delete, no hosted personal-data backend, no required cloud LLM, and no analytics creep.

## 11. Proof Requirements

Green requires current tests/proof for the merged behavior, updated ledgers, updated concept locks, and no broad claims beyond evidence.

## 12. Quarantine / Delete Rules

No source deletion occurs in merge batches. Quarantine/delete happens only in later dedicated cleanup after proof, rescue, owner approval, and rollback.

## 13. Red / Yellow / Green Gates

Red: deletes source before rescue/proof, keeps two active owners, ignores better older code, creates a parallel implementation, bypasses SourceRecord/Receipt/ReplayTrace/You inspection, drops accessibility, drops tests/proof, or claims final consolidation without source proof.

Yellow: owner review remains, rescue is bounded, proof is partial, or retirement is planned but not executed.

Green: one canonical owner, rescue candidates resolved or bounded Yellow, tests/proof updated, duplicate paths classified, retirement/quarantine plan created, no overclaims.

## 14. Required Final Report

Champion Merge final reports must include Status, Concept, Canonical owner before/after, Competing implementations, Better fragments rescued, Active code changed, Runtime wires, SourceRecord, Receipt, ReplayTrace, You inspection, Reset/delete, Tests run, Proof artifact, Supersession ledger update, Best-code rescue ledger update, Concept lock update, Duplicates remaining, Retirement candidates, Yellow/Red items, Claims allowed, and Claims forbidden.

## 15. Rollback Behavior

Rollback only the merge batch files. Do not delete historical/source material as rollback. Preserve proof logs and guard reports as evidence unless the cleanup batch explicitly owns them.
