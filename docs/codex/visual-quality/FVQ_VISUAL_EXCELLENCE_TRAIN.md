Status: Active-scope visual quality train and global-order overlay. Queued ahead of remaining broad visual/platform work after the currently active batch finishes safely.
Date: 2026-05-05
Train code: FVQ

## Purpose

FVQ prevents Ambitions from becoming structurally correct but visually weak. It turns rendered simulator output into blocking evidence, not an advisory artifact.

A batch is not flagship because it compiles. A batch is not flagship because its typed contract exists. A batch is flagship only when the real rendered app looks and feels worthy of Ambitions' canon.

## Required Approval Phrase

`Start Visual Excellence Train`

The global full-stack order may also select FVQ batches when cross-train execution is preauthorized.

## Placement Rule

FVQ must run at the earliest safe point after the current active batch completes. If Codex is already running a batch when FVQ is inserted, Codex must finish, validate, and commit that active batch if safe, then pull latest and run FVQ before continuing broad global work.

Preferred order after FCP09:

1. FVQ01 Rendered Visual Freshness And Flagship Gate — Today.
2. FVQ02 Five Top-Level Surface Visual Sweep — Today, Goals, Capture, Plan, You.
3. FVQ03 Drill-Down And External Surface Visual Sweep.
4. FVQ04 Recurring UI-Batch Rendered Proof Protocol.
5. MEG01 Metal / Advanced Rendering Eligibility Gate.
6. FVQ05 Final Visual Proof Packet integration hook.

## Global Rule

No visible Ambitions surface may close Green solely on compile/tests/docs. Every visible surface must either provide durable rendered evidence or inherit an explicit FVQ owner, Yellow classification, and repair path.

## FVQ01 — Today Rendered Visual Freshness And Flagship Gate

Purpose: prove the current simulator Today view is fresh, durable, scored, and visually worthy.

Hard Red if Today still looks like:

- component proof screen
- scaffold/debug UI
- giant explanatory Reality Rail card
- internal chip/pill labels as primary UI
- generic SwiftUI card stack
- surface
- non-premium shell

## FVQ02 — Five Top-Level Surface Visual Sweep

Purpose: audit all five locked tabs as real simulator output.

Required screenshots:

- Today
- Goals
- Capture
- Plan
- You
- Dynamic Type where tooling permits
- Reduce Motion where tooling permits
- private/source-stale/recovery states where fixtures permit

Top-level pass rules:

- Today: Start Here + Reality Rail must feel like one daily decision surface.
- Goals: LifePath / MissionControlTimeSpine must not become progress-card surface or project management.
- Capture: composer-first starfield capture, not inbox/feed/list.
- Plan: LifeShape instrument, not calendar clone or analytics surface.
- You: Personal System Center, not generic settings dump.

Any top-level screen below bar creates a repair batch before broad continuation.

## FVQ03 — Drill-Down And External Surface Visual Sweep

Purpose: audit flagship drill-downs and external surfaces when they exist.

Targets:

- Step Detail
- Step Session
- Goal Detail / Mission Control
- Memory Lens
- Receipt Drawer
- Weekly Life Sweep
- Appearance Studio
- Schedule / Availability
- widgets
- Live Activities
- App Intents/Shortcuts confirmation surfaces
- notification content previews

External surfaces must be glanceable, privacy-safe, native, and visually consistent with Ambitions without exposing sensitive Found Life content.

## FVQ04 — Recurring UI-Batch Rendered Proof Protocol

Purpose: make FVQ a recurring rule.

Every future UI-affecting batch must:

- list visible surfaces touched
- capture or update rendered screenshots
- score against the relevant visual rubric
- verify simulator/app freshness
- classify visual Yellow/Red honestly
- update visual evidence paths
- avoid Green if rendered output fails

Applies to FCP, PFC external surfaces, AOS UI integration, LDI UI integration, widgets, Live Activities, onboarding, App Store screenshots, and any visible shell changes.

## MEG01 — Metal / Advanced Rendering Eligibility Gate

Purpose: allow advanced rendering only where it creates signature value and does not mask weak UI composition.

Default stack:

1. SwiftUI layout/materials.
2. SwiftUI Shapes.
3. SwiftUI Canvas.
4. Metal only after eligibility proof.

Metal is allowed only for signature visual primitives such as:

- Capture Atmosphere
- LifeShape Contour / Pressure Field
- MissionControlTimeSpine field rendering
- carefully bounded atmospheric/material effects

Metal is forbidden for:

- fixing Today hierarchy
- fixing weak copy
- fixing tab/shell layout
- replacing native controls
- decorative sci-fi effects
- business logic
- navigation
- persistence
- trust/source logic

Metal eligibility requires:

- SwiftUI/Canvas insufficiency proof
- performance/battery budget
- accessibility fallback
- Reduce Motion fallback
- static fallback
- isolated renderer boundary
- screenshot proof
- no gimmick / no sci-fi drift

## FVQ05 — Final Visual Proof Packet Integration Hook

Purpose: integrate FVQ evidence into final FCP28/FCP29/PFC39 handoff.

Final visual proof must include:

- all five top-level screens
- critical drill-downs
- widgets/Live Activities if implemented
- light/dark if supported
- Dynamic Type
- Reduce Motion
- privacy-sensitive states
- empty/loading/degraded states
- overloaded/recovery states
- screenshot freshness proof
- human visual review checklist
- unresolved Yellow owner list

## Required Rubric

Each rendered surface must score:

- Native iPhone believability: 9/10 or higher
- Premium material quality: 9/10 or higher
- One primary object clarity: 9/10 or higher
- Ambitions-specific identity: 9/10 or higher
- Found Life alignment: 9/10 or higher where relevant
- Trust/source/privacy expression: 9/10 or higher where relevant
- Cognitive load: 9/10 or higher
- Accessibility/readability: 9/10 or higher
- Reduced Motion equivalent: 9/10 or higher
- No dashboard/card-stack drift: 10/10
- No scaffold/debug/proof language as primary UI: 10/10
- Screenshot freshness proof: 10/10

## Hard Red

Stop or repair before broad continuation if:

- any top-level tab looks like a dashboard/card pile
- any rendered screenshot looks like a prototype/demo screen
- visual hierarchy is muddy enough that the primary object is unclear
- Plan looks like a calendar clone
- Goals looks like project management
- Capture looks like inbox/feed
- You looks like generic settings dump
- Today looks like internal component proof
- screenshot freshness cannot be proven
- Codex would need to weaken canon to pass

## Completion Standard

FVQ completes only when FVQ01-FVQ05/MEG01 are either Green or accepted Yellow with no Hard Red, durable evidence exists, and the global train has a recurring rule for future UI-affecting batches.
