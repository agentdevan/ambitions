# Flagship Implementation Upgrade Overlay

Overlay ID: `FLAGSHIP_IMPLEMENTATION_UPGRADE_OVERLAY`

Status: active docs/governance overlay after merge. This file changes Ambitions execution governance only; it does not change app behavior, Swift production code, routing, persistence/schema, signing, entitlements, dependencies, AI runtime, LDI runtime, sync/cloud, StoreKit, release configuration, or hosted validation.

## Purpose

Every future Ambitions batch must mature the touched feature, screen, object, primitive, intelligence system, engine, kernel, QA gate, release gate, and proof packet toward 10/10 flagship readiness before claiming implementation completeness.

The overlay upgrades acceptance posture. It does not, by itself, prove that any existing object is flagship-complete.

## Terminal-Device Rule

Physical-device proof is final-only and terminal-only. It is the terminal release-candidate proof gate, not an intermediate discovery phase, exploratory validation pass, or substitute for code/product/design/accessibility/privacy/legal/platform/release gates.

Device proof may begin only after all pre-device gates have closed and a release-candidate proof packet exists.

If a later physical-device gate fails, the release candidate is invalidated and the train routes back to the owning repair batch. No code changes occur inside the device gate.

## Pre-Device Closure Rule

All feature, product-object, primitive, intelligence, source/freshness, accessibility, visual, performance, privacy/legal, platform, release, signed-RC, and claim-safety gates must close before physical-device proof begins.

If any required pre-device gate remains Red, unresolved, unowned, or unproven, the device gate is blocked.

## Hosted-Workflow Rule

GitHub Actions and hosted workflow files are intentionally absent from this repo. Current validation must be local/Codex-operated through checked-in scripts, explicit command logs, proof artifacts, local Xcode/local simulator commands, and terminal gates.

Hosted CI, Actions artifacts, workflow run output, and `.github/workflows/**` are not valid current proof sources for Ambitions governance.

## Object Maturity Rule

Every shipped object needs:

- domain model
- state model
- projection
- UI
- interaction model
- motion and Reduce Motion behavior
- accessibility posture
- privacy/source/trust posture
- fixtures
- focused tests
- rendered proof where visible
- performance budget
- traceability to source truth, owner files, and acceptance gates

A visual or structural implementation alone is not enough for Green if the object lacks the maturity packet required by its domain.

## Intelligence Maturity Rule

Ambitions intelligence must be deterministic-first. Intelligence batches must preserve:

- source-backed claims
- no hidden mutation
- no confidence scores as user-facing truth
- no unsupported source certification
- no chatbot-wrapper posture
- explicit review for consequential recommendations
- source/freshness/privacy labels where claims or personal context affect outcomes

Any model, classifier, adapter, local-language, recommendation, proof, or memory behavior must remain value-model-only until the owning runtime batch proves otherwise.

## Source Atlas / Pack Factory Rule

Source Atlas and Pack Factory source/freshness/provenance/review gates must precede consequential recommendations, generated steps, projection claims, or source-certified explanations.

No batch may fabricate seeds, source packs, official claims, freshness proof, or provenance evidence to advance the train.

## Accessibility Rule

VoiceOver, Dynamic Type, Reduce Motion, non-color meaning, hit targets, cognitive load, and privacy-safe labels are pre-device gates. Public accessibility conformance remains unclaimed until the release/accessibility gate has explicit evidence.

## Visual Rule

Rendered simulator proof and human design review precede device proof for visible UI, shell/chrome, external surfaces, motion states, onboarding, screenshots, and accessibility-presentation states.

Device proof verifies the release candidate. It does not replace rendered proof or design review.

## Release-Claim Rule

Do not claim release readiness, App Store readiness, TestFlight readiness, signed archive readiness, physical-device proof, public accessibility conformance, legal/privacy compliance, platform readiness, sync/cloud readiness, AI runtime readiness, LDI runtime readiness, production model readiness, or hosted CI proof without matching repo evidence.

Unsupported claims are Hard Red conditions.

## Continuation Rule

Only Hard Reds stop the train. Yellow advisories must be parked with owner, reason, follow-up, and recheck condition. Green batches may continue to the next eligible global batch under the current registry, optimized order, and full-stack order.
