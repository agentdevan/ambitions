# Personal Life OS Runtime Law

Status: Active PLOS M00 governance law
Issue: AMB-637 / PLOS-001
Parent: AMB-608 / PLOS-M00
Authority posture: Supporting PLOS law subordinate to `docs/truth/*`
Runtime implementation proof: none

This law operationalizes the active product truth for PLOS execution. It does not supersede `docs/truth/PRODUCT_DESIGN_TRUTH.md`, `docs/truth/PRODUCT_MOAT_TRUTH.md`, `AGENTS.md`, or live source evidence. If this law conflicts with active truth files, the truth files win and this law must be repaired before any dependent issue closes Green.

## Core Thesis

Ambitions does not make the user fit a productivity system.

Ambitions makes goal execution fit the user's life.

Every PLOS phase must preserve that thesis. Ambitions is a local-first Personal Life Operating System: it turns intent, life constraints, sources, time reality, proof, and recovery into inspectable execution. It is not a generic productivity workflow with Ambitions-branded labels.

## What Ambitions Is Not

Ambitions must not be framed, implemented, reviewed, or closed Green as:

- a task app
- a habit tracker
- a chatbot
- a calendar clone
- a productivity dashboard
- a generic AI planner
- a social feed
- an analytics wall
- a life score, productivity score, XP, streak, or shame system
- a cloud-LLM-first planner

The product may contain tasks, calendar replacement behavior, habits, productivity workflows, and local runtime intelligence, but these are subordinate behaviors inside the Personal Life OS. They are not the product category, architecture, or primary user promise.

## What Ambitions Is

Ambitions is:

- a local-first Personal Life Operating System
- a goal-to-life runtime
- a source-aware path compiler
- a Step elasticity runtime
- a cross-goal consequence prevention system
- a proof and receipt fabric
- a living visualization of the user's life
- an inspectable local intelligence layer for fit, reflow, closure, recovery, and replay

The runtime value is not that Ambitions stores goals or steps. The value is that the same intent can produce different, inspectable execution for different local lives, and that completion, interruption, recovery, and proof change future recommendations without shame or hidden mutation.

## Canonical User-Facing Language

Use these terms in current user-facing product language and active PLOS law references:

- Start here
- Recommended step
- Start now
- Open step
- Step

These terms align with active truth files and must remain tied to source, reason, fit, control, receipt behavior, and recovery-aware execution. They must not become generic task-list copy.

## Forbidden Language And Framing

Avoid these terms and frames in current user-facing language and in any Green claim for PLOS runtime behavior:

- task as the primary runtime object
- next best move
- best next move
- Begin Focus
- Plan as a top-level IA object
- productivity score
- XP
- streak pressure
- AI-branded recommendation copy
- shame-based unfinished-state copy
- generic dashboard, feed, analytics wall, or chatbot framing

The word `task` may appear only when describing commodity categories, stale source, compatibility seams, or explicit anti-drift rules. It must not become the primary active runtime object.

## Core Runtime Loop

The PLOS runtime loop is:

```text
Any goal
-> operating mode
-> source/pathing data
-> path options
-> selected path
-> Step graph
-> elastic Step
-> schedule install
-> Today Recommended step
-> completion
-> reflow
-> proof
-> optional share
-> receipt
-> sync
-> replay
```

This loop is a governance contract for later phases, not proof that the loop is implemented. A later implementation issue may claim Green only when live source, validation, and proof artifacts demonstrate its scoped part of the loop without breaking local-first, privacy, or phase-order boundaries.

## UI Posture

PLOS-dependent UI must be:

- simple at rest
- deep on demand
- calm
- recovery-aware
- ADHD/cognitive-load aware
- native iPhone-first
- source, receipt, and trust aware when recommendations or reflow are involved

PLOS-dependent UI must not default to:

- dashboard/card-stack anatomy
- generic task lists
- calendar clone surfaces
- chatbot-first flows
- analytics walls
- guilt, urgency, shame, streak, or score pressure

No UI issue can claim product Green if the visible experience violates this law, even if it compiles or passes a narrow script.

## Green Enforcement

Future PLOS issues cannot close Green when their scoped result violates this law.

At minimum, a PLOS closeout that depends on runtime/product behavior must state:

- the live `AMB-*` issue identifier used for Linear work
- which part of the Personal Life OS runtime loop is in scope
- how the change preserves local-first, inspectable, proof-aware behavior
- why it does not collapse into a task app, habit tracker, dashboard, calendar clone, chatbot, generic AI planner, social feed, analytics wall, score, XP, or shame mechanic
- whether app source, runtime behavior, UI, privacy, accessibility, performance, release, or device proof was actually changed or verified

Green requires scoped proof. Yellow is allowed for named evidence gaps with an owner and no readiness overclaim. Red is required for category collapse, stale IA, PLOS label Linear access, phase-order violation, private data/R2 boundary risk, required cloud LLM core dependency, or implementation claims without evidence.
