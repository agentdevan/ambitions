## Purpose

These criteria define when Ambitions behavior is actually end-game product behavior rather than component installation.

## Universal Criteria

A moat-runtime feature is accepted only when it satisfies all applicable criteria:

1. **Object-first**: It is built around a durable Ambitions object, not a generic card/page/module.
2. **Loop-aware**: It contributes to at least one end-to-end product loop.
3. **Local-first**: It does not require hosted personal data, external/cloud LLM, or hidden backend processing.
4. **Inspectable**: The user can see why Ambitions acted or recommended.
5. **Correctable**: The user can repair wrong routing, source interpretation, recommendation, or learning.
6. **Receipted**: Meaningful changes leave a receipt or trace.
7. **Recovery-aware**: Broken plans can recover from the last honest point.
8. **Accessibility-aware**: Meaning is not visual-only or motion-only.
9. **Anti-generic**: The feature could not ship unchanged inside a generic task/calendar/notes/chatbot app.
10. **Proof-honest**: The report does not claim more than current validation proves.

## Surface Criteria

### Today / Reality Meridian

Accepted only when Today can show current reality, recommended step, fit reason, trust path, action start, closure, receipt, and recovery/reflow state.

### Goals / Constellation Atlas

Accepted only when Goals expresses Ambition Graph relationships, proof continuity, commitments, alternate paths, and non-dashboard visual structure.

### Capture / Atmosphere Composer

Accepted only when Capture can classify/reroute to proof, source, constraint, commitment, reflection, goal seed, held item, or ready-to-place action without becoming an inbox feed.

### Time / LifeShape Field

Accepted only when Time shows capacity, pressure, protected/open time, horizon context, and reflow implications without becoming a calendar clone.

### You / User System Profile

Accepted only when You exposes Personal Runtime, local learning, trust, automation, data controls, receipts, and reset/delete controls without becoming a social/admin/profile page.

## Proof Criteria

A batch may be marked Green only if focused proof for the touched owner ran and passed.

Use Accepted Yellow when proof is blocked by named environment/simulator/tooling issues but source scope is clean and no readiness claim is made.

Use installed_unverified when intentionally installing in proof-light mode without focused proof.

## Hard Red Conditions

- Generic productivity UI.
- Hidden recommendation logic with no Why This? path.
- Closure language that shames incomplete execution.
- Personal data sent to external/cloud LLM or hosted backend as core behavior.
- Plan restored as top-level tab.
- Unsupported release/readiness/accessibility/device/performance/privacy/legal claim.
- Visual runtime completion claimed from docs/control-plane only.
