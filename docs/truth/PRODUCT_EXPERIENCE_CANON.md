## 0. Why this file exists

Ambitions has product/design canon and moat canon, but those files do not fully define the intended product experience.

This file defines the missing bridge between:

product identity  
→ Private Life Runtime  
→ feature behavior  
→ user experience  
→ implementation direction  
→ proof gates

Ambitions must not become a loose collection of tabs, task controls, calendar views, AI-sounding copy, static plans, disconnected runtime models, or generic productivity features.

Ambitions must become a native, local-first Personal Life OS that can:

1. Learn the user intimately from input, behavior, proof, schedule reality, resources, constraints, and lived patterns.
2. Generate full scheduled paths for every goal.
3. Continuously adjust the future when reality changes.
4. Preserve Life Capital from prior skills, proof, accomplishments, resources, relationships, and experience.
5. Help the user accomplish goals they previously could not accomplish because they did not know the steps, timing, requirements, or path.
6. Simulate conflicts honestly and offer resolution options.
7. Remain simple at the surface and deep underneath.
8. Never force.

This file defines that product experience.

`PRIVATE_LIFE_ORCHESTRATION_TRUTH.md` defines the supreme product mission and core loop: Intent -> Context -> Path -> Time Fit -> Reflow -> Action -> Proof -> Learning. Product-experience behavior in this file must serve that loop and must not turn Ambitions into separate task, calendar, habit, chatbot, dashboard, or cloud-backed private-life-graph products.

`PRODUCT_ORIGIN_TRUTH.md` defines why Ambitions must serve high-agency users with more ambition than operating structure. This canon turns that origin problem into behavior contracts, actionability, scenario gates, and proof requirements.

This file does not prove implementation exists, tests pass, the app is release-ready, the runtime is complete, or the current UI satisfies this canon. Proof requires code, tests, device validation, screenshots, accessibility validation, privacy validation, and owner acceptance.

## Layer 1 — Product Experience Law

### 1. North Star

Ambitions is a private external brain that carries the user’s life context forward.

It learns how the user operates, preserves Life Capital from prior proof and accomplishments, generates full scheduled paths for every goal, and continuously adjusts the future so ambition fits real life.

Ambitions may suggest, schedule, warn, simulate, protect, and adjust, but it must never force. The user remains the final authority.

### 2. Core Product Experience Thesis

Ambitions becomes magical when it understands:

* where the user is
* who the user is
* what resources the user has
* how the user operates
* what restraints the user faces
* what skills and accomplishments the user already has
* what patterns have stopped the user from being ambitious
* what steps are required to accomplish goals the user could not previously accomplish
* when a pivot to a related or better-fitting goal makes sense

Ambitions is no longer a productivity app when every user’s app becomes meaningfully different because every user’s life context, capabilities, proof, constraints, priorities, schedule, and lived behavior are different.

### 3. Permanent Product Promise

Ambitions helps the user:

1. Capture anything meaningful.
2. Turn goals into full scheduled paths.
3. Understand what life can actually hold.
4. Start with what fits now.
5. Preserve progress and proof.
6. Carry skills and accomplishments forward.
7. Adjust when reality changes.
8. Simulate conflicts before committing.
9. Make room for what matters.
10. Stay in control.

The product promise:

Ambitions carries your life context forward so your future path can keep adapting to who you are, what you have, what you have proved, and what reality can hold.

### 4. Force Nothing Law

This is a top-level product-experience commandment.

Ambitions may suggest, schedule, warn, simulate, protect, and recommend, but it must never force. The user remains the final authority.

There are no exceptions.

The user must always have options.

Ambitions must never force:

* a goal
* a Step
* a deadline
* a schedule change
* an adjustment
* a priority
* a pause
* a deletion
* a shared path
* a sensitive inference
* a behavioral interpretation
* a notification style
* an automation level

Ambitions may make consequences clear. It may say something does not fit. It may recommend changes. It may show conflicts. It may suggest pausing another goal. But the user decides.

## Layer 2 — Foundation Requirements

### 5. Foundation Is Not MVP

Ambitions must be best-in-class at its foundation layer.

This is not an MVP compromise.

Before Ambitions can become a market-defining Personal Life OS, it must be excellent at:

* reminders
* simple Steps
* recurring tasks
* calendar planning
* quick Capture
* basic goals
* scheduling
* rescheduling
* deadline handling
* conflict handling
* notifications
* search
* completion
* missed-work recovery
* review
* local persistence
* offline use

If the foundation feels weak, the runtime will not matter.

### 6. Replacement-Level Planning Product

Ambitions should eventually replace Apple Reminders and Apple Calendar for the user’s personal planning experience.

It may still ingest Apple context where permissioned.

Ambitions should not merely mirror Calendar or Reminders. It should absorb their core utility and then add what they cannot provide:

* goal pathing
* Life Capital
* proof preservation
* capacity-aware scheduling
* Future Step adjustment
* conflict simulation
* recovery
* personalized planning
* local inspectability

### 7. Thin Use and Deep Use

Ambitions must support thin use and deep use.

Thin use:

* reminders
* quick Capture
* simple Steps
* basic goals
* calendar planning
* recurring tasks

Deep use:

* full-path generation
* Life Capital
* goal simulation
* capability-aware planning
* proof carryover
* long-term Future Steps
* cross-goal conflict resolution
* week/month/year reviews
* local learning
* automation control

Product law:

Simple at the top. Deep under the object. Never shallow underneath.

## Layer 3 — Learning the User

### 8. Local Learning Law

Ambitions should learn the user intimately.

Learning may come from:

* explicit user input
* passive behavior
* schedule patterns
* goal completion speed
* recurring obstacles
* moved Steps
* skipped Steps
* ignored recommendations
* accepted recommendations
* abandoned goals
* protected time
* proof
* resources
* credentials
* accomplishments
* energy patterns
* follow-through patterns
* repeated conflicts
* missed deadlines
* review outcomes
* Apple data sources where permissioned
* future third-party sources where approved

Learning must remain:

* local-first
* private
* inspectable where appropriate
* user-controlled
* archive/delete aware
* non-coercive
* non-shaming

### 9. Passive Learning Is Allowed

Ambitions may learn from passive behavior.

Passive signals may include:

* repeatedly moving Steps
* completing certain Step sizes more often
* finishing faster or slower than expected
* skipping certain Step types
* ignoring recommendations
* adding proof
* protecting time
* abandoning or pausing goals
* repeatedly creating similar goals
* consistently using or avoiding specific time windows
* completing work in specific contexts
* failing to complete work in specific contexts

Passive learning should shape the app experience.

It should not become creepy, accusatory, or notification-heavy.

### 10. No Emotional Labeling

Ambitions may infer behavioral obstacles.

Ambitions must not emotionally label the user.

Avoid:

* avoidance
* anxiety
* laziness
* lack of motivation
* burnout
* fear
* discipline failure
* procrastinator
* uncommitted

Prefer behavior-first language:

Evenings have not been holding this.  
Shorter Steps have worked better here.  
This goal keeps losing space when the week fills.  
Your weekend windows have carried most music progress.

### 11. Learning Surfaces

Learning should primarily affect:

* path generation
* scheduling
* Future Steps
* priority suggestions
* simulation
* conflict resolution
* Life Capital
* reviews
* broad stats
* in-app recommendations

Learning insights should appear inside the app, not as aggressive personal notifications.

The Memory Vault should remain mostly inside the runtime.

The user should see:

* broad stats
* learning controls
* user-input settings
* Life Capital
* visible Patterns
* high-level factors that shaped passive learning

The user should not see a giant exposed psychological dossier.

## Layer 4 — Memory, Archive, and Delete

### 12. Memory Duration

Ambitions remembers forever until the user deletes.

Memory should not silently expire by default.

Ambitions may mark context as stale, archived, or no longer influential, but it should not erase meaning without user action.

### 13. Archive and Delete

User-facing memory controls should be simple:

Archive  
Delete

Archive:

* preserves the item in history
* keeps it searchable
* stops it from influencing future planning
* preserves past context

Delete:

* removes the item
* removes future planning influence
* removes it from search/history where technically possible
* must be clear and intentional

### 14. Sensitive Context

Ambitions may use sensitive context if the user provides it and it remains within the approved local/private product boundary.

Sensitive context must not become:

* lock-screen disclosure
* cloud profiling
* server-side inference
* psychological scoring
* hidden manipulation
* aggressive notifications

## Layer 5 — Full Goal Path Generation

### 15. Any Goal Law

Ambitions must support every goal type.

This includes:

* one-Step goals
* short-term goals
* long-term goals
* lifelong goals
* physical goals
* mental goals
* financial goals
* relationship goals
* creative goals
* career goals
* learning goals
* home/life administration goals

Any goal is valid input.

When Ambitions cannot fully path a goal, it should not fail generically. It should ask clarifying questions and preserve progress.

### 16. Full Path Requirement

When a user creates a goal, Ambitions should generate the full path immediately.

A full goal path may include:

* high-level path
* phases
* milestones
* Step graph
* first proof target
* requirements
* prerequisites
* resources
* risks
* blockers
* weekly cadence
* Time placement
* recovery plan
* review loop
* alternate paths
* conflict simulation
* Future Steps

With user context plus deadline, Ambitions should build, map, and schedule every Step needed to accomplish the goal.

### 17. Living Visual Path

A goal path should feel like:

* a strategic roadmap
* a living training plan
* a project plan
* a guided quest
* a personal operating path

But Ambitions must not become gamified.

The product expression:

A live visual path guiding the user from today until accomplishment.

### 18. Path Generation Pipeline

Canonical pipeline:

Capture / Goal input  
→ clarification when needed  
→ goal understanding  
→ primary interpretation  
→ alternate interpretations when needed  
→ Source Atlas match where useful  
→ requirement projection  
→ Life Capital match  
→ capability/resource/proof context  
→ full path generation  
→ full-path scheduling  
→ Future Steps  
→ conflict simulation  
→ Today schedule slice  
→ Step execution  
→ closure  
→ proof  
→ review  
→ adjustment  
→ learning update

### 19. Vague Goal Handling

When a goal is vague, Ambitions should ask clarifying questions.

It should not generate a fake confident path from unclear input.

However, the user should be able to skip or answer partially without losing progress.

Ambitions may create a provisional goal shell while clarification continues.

## Layer 6 — Full-Path Scheduling and Future Steps

### 20. Everything Is Scheduled

Ambitions does not create vague someday goals.

It turns goals into scheduled reality.

Every goal should become a scheduled path.

### 21. Immediate Full-Path Placement

When a goal is created, the full path should be placed immediately.

For near-term goals, this may mean concrete Step placement.

For long-term or lifelong goals, this may mean flexible scheduled Future Steps across time windows.

### 22. Future Steps

User-facing term:

Future Steps

Future Steps are flexible scheduled path nodes.

They may live weeks, months, or years ahead.

They should appear lightly and abstractly enough that Time does not become visually overwhelming.

Future Steps should use time windows.

Examples:

Draft outline sometime Tuesday evening.  
Record vocals during the March 10–14 window.  
Build endurance base across April.  
Review financial documents before June.

### 23. Lifelong Goals

Lifelong goals require both:

* actual lifelong cadence
* renewable rolling horizon

Ambitions should not fake a complete lifelong plan as if life will not change.

It should create durable cadence and continually renew the path through review, proof, reality, and user direction.

### 24. Editing Future Steps

Near-term Future Steps behave like normal editable Steps.

Far-future Future Steps should open a path-impact preview before changes apply.

Example copy:

Changing this Future Step affects 2 milestones and 5 later Steps.

The user may still proceed.

## Layer 7 — Continuous Adjustment and Protected Future

### 25. User-Facing Language

Avoid exposing “reflow” as primary user-facing language.

Use simpler verbs:

* Adjust plan
* Update path
* Make this fit
* Resolve conflict
* Rebuild schedule
* Make room
* Lower pace
* Change deadline

“Reflow” may remain internal.

### 26. Automatic Future Adjustment

Ambitions should silently adjust the future by default.

Silent automatic movement is forbidden inside the internal protected near-term window.

That protected window is internal only. Do not make it a branded user-facing object.

### 27. Seven-Day Placement Protection

Working implementation rule:

Ambitions must not silently move scheduled placement inside the next seven days.

Inside the protected seven-day window, placement changes require user awareness and approval.

This rule applies to placement, not necessarily Step content.

### 28. User-Caused Adjustment

When the user causes an adjustment by adding a new Step, adding a new Goal, changing a deadline, changing a constraint, or creating a conflict, Ambitions should show the impact.

It should not silently rearrange the user’s near future.

### 29. Ignored Plan Behavior

When a user ignores the plan for several days, Ambitions should ask what changed and respond based on context.

Possible responses:

* ask for closure
* make the plan lighter
* preserve the goal but reduce pressure
* suggest pause or defer
* protect recovery
* update Future Steps
* adjust outside the protected near-term window
* ask what changed

## Layer 8 — Simulation and Conflict Resolution

### 30. Simulation Is Core

Simulation is a core runtime capability.

Ambitions should let the user test:

What happens if I add this goal?  
What happens if I change this deadline?  
What happens if I cancel this conflict?  
What happens if I protect evenings?  
What happens if I pause this area?  
What has to change to make this possible?

### 31. Honest Capacity

Ambitions must honestly say when the user cannot accomplish everything by a deadline with current constraints.

It should preserve ambition while refusing fake schedule success.

Preferred copy:

This does not fit yet.

Avoid:

* impossible
* failed
* overloaded
* too ambitious
* you cannot do this
* Ambitions recommends you do not do this

### 32. Capacity Warning

Default warning:

This does not fit yet.  
Adding this goal would overfill your current plan. Ambitions can help you make room by moving flexible Future Steps, changing the deadline, lowering the pace, pausing another goal, or protecting a lighter path.

Short UI version:

This does not fit yet.  
Make room, change the deadline, lower the pace, or add it with conflict.

Actions:

* Make room
* Change deadline
* Lower pace
* Pause another goal
* Add with conflict

### 33. Add With Conflict

If a goal does not fit and the user chooses to add it anyway, Ambitions should create the goal and path, but keep the conflict visible until resolved.

It should not silently wreck the schedule.

Behavior:

1. Create the goal.
2. Generate the full path.
3. Place Future Steps where possible.
4. Mark conflicts visibly.
5. Do not silently move anything inside the protected near-term window.
6. Show a clear conflict state until the user resolves it.

Copy:

Added, but it needs room.  
Ambitions created the path, but your current plan cannot hold it yet. Make room, lower the pace, change the deadline, pause another goal, or leave the conflict visible.

Actions:

* Make room
* Lower pace
* Change deadline
* Pause another goal
* Leave conflict visible

## Layer 9 — Priority

### 34. Priority Model

User-facing Priority:

Low  
Normal  
High

Do not use “Critical” as a default visible priority label.

Do not use “Must Fit” as a goal type.

### 35. Make Room

When a goal does not fit, the user may choose:

Make room for this

A goal is not inherently “Must Fit.” The user decides whether it matters enough for Ambitions to help make room.

### 36. Priority Doctrine

Priority tells Ambitions how much a goal matters.

When a goal does not fit, the user may choose to make room.

Ambitions may suggest moving flexible Future Steps, changing pace, changing deadlines, or pausing lower-priority goals, but it must not force those changes.

### 37. Priority Inputs

Priority is both inferred and user-controlled.

Runtime priority may consider:

* user override
* deadline pressure
* identity relevance
* capacity cost
* conflict cost
* proof momentum
* life-area importance
* dependency pressure
* opportunity window
* recovery cost
* current schedule pressure
* ignored/moved history

User-facing law:

Priority belongs to the user. Ambitions may infer pressure and suggest changes, but the user can always override it.

## Layer 10 — Life Capital

### 38. Life Capital Definition

User-facing name:

Life Capital

Life Capital is the skills, credentials, resources, relationships, accomplishments, proof, patterns, and lived experience Ambitions uses to avoid treating the user like a beginner.

Internal models may include capability graphs, proof resource graphs, personalization ledgers, source claims, and correction folds.

The user should not need to understand those internals.

### 39. Life Capital Contents

Life Capital may include:

* capabilities
* credentials
* licenses
* degrees
* certifications
* employment history
* education
* skills
* relationships
* mentors
* trainers
* coworkers
* accountability partners
* resources
* equipment
* tools
* subscriptions
* locations
* proof
* accomplishments
* reusable assets
* patterns
* repeated successful behavior
* user-stated ability
* imported evidence where approved

Examples:

* driver’s license
* high school diploma
* college degree
* can cook
* plays guitar
* can record vocals
* can run 3 miles
* has recording equipment
* knows Logic Pro
* has shipped SwiftUI screens
* has a mentor
* has handled a similar project before

### 40. Life Capital as Planning Input

Life Capital is not a badge system.

It is a planning input.

When Ambitions has proof or user input that the user can already do part of a new goal, the generated path should become shorter, smarter, or more advanced.

Example:

If the user has recorded vocals before, Ambitions should not treat a new music goal as starting from zero. It should not mark new vocals complete, but it should know vocal recording is an existing capability.

### 41. Capability Shape

Capabilities are contextual, blended graph nodes.

Do not expose rigid levels like Level 1 / Level 2 / Level 3.

A capability may be shaped by:

* proof exists
* recency
* repeatability
* credential
* independence
* difficulty handled
* domain relevance
* resource access
* context similarity
* user-stated ability
* linked goals
* linked Steps
* linked proof
* linked resources
* user corrections

### 42. Manual Editing

Capabilities and other Life Capital are manually editable.

When the user edits Life Capital, Ambitions must understand the change and update relevant paths accordingly.

Copy:

This changes 3 paths.  
Ambitions can update Future Steps for Music, Fitness, and SwiftUI based on this change.

Actions:

* Review changes
* Update paths
* Keep for later
* Undo edit

### 43. Automatic Inference

Ambitions may infer capabilities from repeated Step completion without direct user confirmation.

It may also infer capabilities from proof, credentials, accomplishments, and repeated successful behavior.

This inference should remain local and inspectable at the broad level.

### 44. No Automatic Decay

Capabilities do not decay automatically.

The user can remove, archive, or correct them if needed.

Ambitions may mark something as needing review when context changes, but it should not silently erase Life Capital.

### 45. Patterns

Patterns live inside Life Capital.

Patterns are user-visible planning stats, not exposed surveillance.

Examples:

Evening gym Steps moved 4 times this month.  
Music work fits better on weekends.  
Short Steps completed more often than long blocks.  
Goals with proof attached were easier to continue.

Patterns may affect planning, but should be communicated through broad, useful stats.

## Layer 11 — Proof and Progress Preservation

### 46. Proof Law

Proof is optional but valuable.

Proof works on the honor system.

Ambitions should not grade proof as weak, supporting, strong, or decisive.

If the user lies, they distort their own experience. Ambitions should not become a proof-policing product.

### 47. Proof Types

Proof may include:

* completed Step
* photo
* file
* note
* reflection
* calendar evidence
* external artifact
* repeated behavior
* user confirmation
* receipt
* milestone
* blocker resolved
* feedback received
* decision
* resource created
* result produced

### 48. Progress Is Never Lost

When a goal changes or pivots, previous progress should transfer as context, proof, skill, resource knowledge, or capability knowledge.

Transfer must not create false completion.

Example:

If the user recorded vocals for one song, Ambitions should not mark vocals complete for a different song. But it should know the user has recorded vocals before and should not treat vocal recording as starting from zero.

### 49. Progress Transfer Language

Preferred:

You are not starting from zero.

Avoid:

This proof does not apply.

Better distinctions:

* this helps the new path
* this proves a capability
* this is context
* this does not complete the new Step

### 50. Still Counts

“Still counts” is a core emotional and functional product behavior.

It means:

* progress is preserved
* proof remains useful
* recovery does not erase the thread
* a pivot is not a failure
* the user is not starting from zero

## Layer 12 — Source Atlas

### 51. Source Atlas Role

Runtime personalizes.

Source Atlas provides external information.

Source Atlas may provide:

* domain packs
* public requirements
* versioned reference packs
* provenance and freshness receipts
* skill ladders
* skill-transfer surfaces
* eligibility rules
* deadlines
* credential and education context
* occupation and career-cluster context
* templates
* reference paths
* examples
* resource hooks
* domain-specific planning structures

### 52. Invisible by Default

Source Atlas should be invisible by default.

Users should not browse packs, install packs, or manage a template marketplace.

Full-fledged built-in packs should be accessible and enabled for everyone at all times where available.

R2 may support freshness and new packs as they are created.

Source Atlas Foundry and any future pack factory are infrastructure, not product surfaces. They may create, validate, diff, and publish public/reference packs, but they must not become user-facing pack management, marketplace browsing, or private-user context collection.

### 53. Runtime Boundary

Source Atlas knows public/reference structure.

Private Life Runtime knows the user.

Ambitions combines them locally into an inspectable path.

Source Atlas must not receive private user context, goals, proof, schedule assumptions, behavior history, or the private life graph.

### 54. Source Inspection

Ambitions should not show when a path used external/reference knowledge by default.

When the user asks why, or when source freshness materially changes path behavior, Ambitions may show a calm inspection view.

Do not make Source Atlas a visible product center.

## Layer 13 — Onboarding / Setup & Personalization

### 55. Onboarding Style

Onboarding should be a conversational guided interview.

It is not a chatbot center and not a static checklist.

It should feel like setting up a private external brain.

### 56. Chapters

Onboarding uses chapters.

Chapters should remain available later in:

You → Setup & Personalization

The user can finish skipped sections, revise old answers, or update context later.

### 57. Save Behavior

Every answer saves immediately.

The user can quit midway without losing entered context.

Every question should be easy to skip.

Skipping should not erase progress or data already entered.

### 58. Progress

Onboarding progress should show as a percentage.

Progress should be weighted by runtime usefulness, not simple question count.

Higher-weight context may include:

* schedule constraints
* calendar access
* first goal
* Life Capital
* automation preference
* current obligations
* data sources
* deadline context

### 59. First Goal

Onboarding should recommend adding a first goal but allow skipping.

Ambitions should not require a goal before the app becomes usable.

### 60. Onboarding Chapters

Canonical chapters:

1. Direction
2. Current Schedule
3. Goals
4. Energy & Work Style
5. Resources
6. Life Capital
7. Obstacles
8. Data Sources
9. Automation
10. First Path Preview

### 61. First-Run Questions

Ambitions should ask questions that quickly improve pathing.

Direction

* What are you trying to become or build right now?
* What areas of life should Ambitions help with?
* Are there any goals you already know matter?
* Are there any goals you are unsure about but keep thinking about?
* What would make Ambitions worth keeping after 30 days?

Current Schedule

* What does a normal week look like?
* What days or times are usually unavailable?
* What recurring obligations should Ambitions respect?
* What usually breaks your plans?
* What do you wish your week had more room for?

Energy & Work Style

* When do you usually have the most energy?
* When do you usually need lighter work?
* Do you prefer small frequent Steps or longer focused blocks?
* Do you work better with deadlines, routines, or flexible options?
* What types of plans usually fail for you?

Resources

* What tools, spaces, equipment, subscriptions, or people help you make progress?
* Do you have transportation constraints?
* Do you have money or budget constraints Ambitions should consider?
* Are there resources you often forget to use?
* Are there resources you need before certain goals can start?

Life Capital

* What skills, credentials, or experience should Ambitions know you already have?
* What have you already accomplished that future goals should build on?
* What are you comfortable doing without beginner setup?
* What should Ambitions not assume you can do yet?
* Are there skills or resources you want Ambitions to reuse in future paths?

Obstacles

* What usually stops you from following through?
* What kinds of Steps do you tend to move or avoid?
* What time of day tends not to work?
* What drains your plan fastest?
* What should Ambitions protect you from overcommitting to?

Data Sources

* Should Ambitions use Calendar to understand fixed time?
* Should Ambitions use Reminders to import existing commitments?
* Should Ambitions use Health/Fitness context if available?
* Should Ambitions use Focus mode or location context if enabled later?
* Should Ambitions keep everything local unless you explicitly approve account/reference features?

Automation

* How much should Ambitions adjust your future plan automatically?
* Should Ambitions ask before changing this week?
* How should Ambitions handle missed Steps?
* Should Ambitions protect recovery time automatically?
* Do you want ambitious plans, conservative plans, or balanced plans?

First Path Preview

* What goal should Ambitions help with first?
* Is there a deadline?
* Why does this matter?
* What would count as progress this week?
* What would prove this path is working?
* What could block it?

Then Ambitions generates:

* full path
* scheduled Future Steps
* first seven-day plan
* conflicts
* capacity warning if needed
* options to adjust before committing

Ambitions supports:

* Week in Review
* Month in Review
* Year in Review

Reviews are user-launched.

They should not be forced rituals.

### 63. Review Purpose

Reviews are both reflective and operational.

They should:

* celebrate accomplishments
* preserve proof
* show what still counts
* show what changed
* show broad learning stats
* update Life Capital
* identify goals that advanced
* identify goals that need room
* show path adjustments
* help the user change the future

### 64. Review Tone

Reviews should feel like:

restrained Spotify Wrapped + personal operating review

They should be:

* fun
* visual
* accomplishment-centered
* useful
* private
* exportable
* not gimmicky
* not social-media cringe

You moved more than it felt like.  
You are not starting from zero next month.

### 65. Export

Reviews should be exportable.

Supported targets:

* Markdown
* PDF
* native share sheet

Later export destinations may include:

* Files
* Apple Notes
* Mail

### 67. Private by Default

Ambitions needs review.

You keep avoiding your music goal.

* What fits now?
* What is protected?
* What is next?
* What needs closure?
* What changed?

* What stage am I in?
* What Future Steps are ahead?
* What proof exists?
* What Life Capital helps?
* What conflicts or assumptions matter?
* What changed since last review?

Time shows whether all goals can actually fit together.

Time should answer:

* Can this fit?
* Where does it fit?
* What is over capacity?
* What is protected?
* What can move?
* What conflicts with this?
* What future windows are carrying the path?
* What happens if I add this goal?

* broad stats
* data sources
* privacy
* capabilities
* user input settings
* automation
* memory archive/delete
* review exports
* runtime controls

### 74. Search

Search can search:

* capabilities
* Life Capital
* proof
* learned patterns
* goals
* Steps
* Future Steps
* history
* resources
* settings
* local data

Search is local-first Find / Ask / Act / Inspect.

Find remains deterministic and offline. Ask is optional, on-device, grounded in eligible local objects, session-local, and object-led; it may offer a Capture handoff, while any Act remains proposed-only until the canonical owner validates and commits it. Search must not become chatbot search, hosted AI, or a path for private-graph transfer.

## Layer 17 — Automation

### 75. Automation Levels

Ambitions should have user-managed automation levels.

Automation should be configurable:

* globally
* per life area
* per goal

Potential levels:

* Manual
* Suggest
* Preview changes
* Auto-adjust future outside protected near-term placement
* Full autopilot for selected goals

Exact labels require implementation-level naming approval, but the behavioral capability is canon.

### 76. Automation Law

Automation never overrides Force Nothing Law.

Ambitions can suggest and preview. It can auto-adjust future placement only where the user has allowed it and where protected near-term placement is not silently changed.

High-stakes areas do not require stricter confirmation by default under this canon.

The universal rule remains:

User always has options. Ambitions never forces.

## Layer 21 — Implementation Horizons

### 88. Horizon Labels

Every feature or implementation train should be labeled:

* Foundation Requirement
* Core Runtime Requirement
* Moat Requirement
* Future Expansion
* Reserved / Not Yet Approved

### 89. Foundation Requirement

Foundation Requirements are required for Ambitions to feel useful as a standalone personal planning product.

A Foundation feature may be simple, but it must be real, polished, local-first, and native.

Examples:

* reminders
* Steps
* recurring tasks
* quick Capture
* scheduling
* calendar planning
* search
* notifications
* basic goals
* local persistence
* conflict visibility
* completion/closure

### 90. Core Runtime Requirement

Core Runtime Requirements make Ambitions behave like a Personal Life OS instead of a task/calendar app.

They connect goals, Steps, Time, proof, Life Capital, learning, scheduling, and adjustment.

Examples:

* full path generation
* full-path scheduling
* Future Steps
* priority
* capacity fit
* conflict simulation
* protected near-term placement behavior
* learning from user behavior
* proof preservation
* Life Capital
* plan adjustment

### 91. Moat Requirement

Moat Requirements create the long-term advantage.

They are hard to copy because they depend on local history, proof, behavior, Life Capital, pathing, and schedule reality accumulating over time.

Examples:

* every user’s path differs
* Life Capital shortens or changes future paths
* progress transfers across pivots
* broad user patterns improve planning
* simulation shows tradeoffs
* long-term Future Steps adjust continuously
* reviews update future planning
* Source Atlas combines with local context without receiving private data

### 92. Future Expansion

Future Expansion may include:

* shared goals
* LinkedIn import
* richer third-party data sources
* expanded Source Atlas packs
* richer export formats
* family/household planning
* collaborative proof
* advanced Life Capital imports
* user-owned sync when separately approved

### 93. Reserved / Not Yet Approved

Reserved concepts require separate canon before implementation:

* hosted private life graph
* cloud AI core planning
* social sharing feeds
* public profiles
* third-party behavioral analytics
* marketplace-style pack browsing
* shared goal sync architecture
* personal-data backend

### 97. Goal Creation Contract

Inputs

* goal title or captured intent
* optional deadline
* optional priority
* optional life area
* optional user context
* available Life Capital
* available schedule context
* available Source Atlas context where relevant
* current automation settings

Runtime action

Ambitions must clarify vague goals, understand the goal, generate a full path, schedule Future Steps, simulate capacity, and detect conflicts.

Output

* goal object
* full path
* scheduled Future Steps
* first near-term schedule slice
* conflict state
* capacity state
* priority state
* proof target
* review points
* adjustment options

goal_creation_generates_scheduled_path_or_clarification

## Layer 25 — Edge-Case Doctrine

### 123. Vague Goal

When a user enters a vague goal, Ambitions must ask clarifying questions.

It may preserve a provisional goal shell.

It must not fake a confident path.

Example:

User enters: Get healthier.  
Ambitions asks what healthier means: strength, endurance, weight, energy, labs, food, sleep, consistency, or something else.

### 124. Impossible Deadline

When a goal cannot fit by the deadline, Ambitions must say so calmly and offer options.

Preferred:

This does not fit yet.

Options:

* change deadline
* lower pace
* reduce scope
* pause another goal
* make room
* add with conflict

Ambitions must not pretend the schedule works.

### 125. User Adds Goal Anyway

If the user chooses Add with conflict:

* create the goal
* generate the full path
* schedule what can be scheduled
* keep conflict visible
* do not silently move protected near-term placement
* keep resolution options available

### 126. New Goal Conflicts With Tomorrow

If a new goal conflicts with a Step tomorrow, Ambitions must not silently move tomorrow’s Step.

It must show the conflict and ask the user to approve any near-term placement change.

### 127. Calendar Conflict Appears Inside Protected Near-Term Window

If a new calendar conflict appears within the protected near-term window, Ambitions must show awareness.

It may suggest moving, shrinking, or replacing affected Steps.

It must not silently move placement.

### 128. Calendar Conflict Appears Outside Protected Near-Term Window

If automation allows future adjustment, Ambitions may silently adjust placement outside the protected near-term window.

It should keep receipts/history available.

### 129. User Misses a Step

When the user misses a Step, Ambitions should ask what changed.

It may offer:

* Still counts
* Move it
* Make lighter
* Blocked
* Not needed
* Pause related path
* Protect recovery

It must not shame.

### 130. User Repeatedly Moves the Same Step

Ambitions may infer a broad pattern and adjust future planning.

It should not emotionally label the user.

Preferred:

This time window has not been holding this Step.

### 131. User Deletes Life Capital

Deleted Life Capital must no longer influence future planning.

If deletion affects active paths, Ambitions should show affected paths.

### 132. User Archives Life Capital

Archived Life Capital remains in history/search but stops influencing future planning.

If archive affects active paths, Ambitions should show affected paths.

### 133. User Edits Life Capital

When Life Capital changes, Ambitions must resimulate affected paths and show impact.

Example:

This changes 3 paths.

### 134. User Pivots a Goal

When a goal pivots, Ambitions must preserve progress.

Progress may transfer as:

* context
* proof
* skill
* resource knowledge
* Life Capital
* accomplishment

It must not falsely complete new work.

### 135. Old Proof Seems Unrelated

Ambitions should not say old proof “does not apply.”

Instead, it should classify it quietly as context or Life Capital when relevant.

Preferred:

This is still part of your history.

### 136. User Lies in Proof

Ambitions works on the honor system.

If the user lies, they distort their own experience.

Ambitions should not over-police proof.

### 137. User Skips Onboarding

Skipping onboarding must not block the app.

Ambitions should continue with lower context and invite completion later in Setup & Personalization.

### 138. User Declines Data Sources

Ambitions must still work.

It may ask for manual context.

It must not block core value because Calendar, Reminders, Health, Focus, or other sources are unavailable.

### 139. Source Atlas Unavailable

If Source Atlas is unavailable, Ambitions must still support local planning.

It may use generic starter paths, ask clarifying questions, or mark external context as unavailable.

It must not send private context to recover missing packs.

### 140. Review Suggests Future Changes

Reviews may suggest future path changes.

They must not apply operational changes without user approval.

### 141. Goal Suggestion From Pattern

Ambitions may suggest a goal based on patterns.

Preferred copy:

This might be worth turning into a goal.

Ambitions must never create a goal without approval.

### 142. Shared Goal Request

Shared goals are future canon.

If a user asks for shared goal behavior before shared-goal architecture exists, Ambitions should explain that shared goals are not available yet and preserve the personal goal locally.

Do not create hidden shared data behavior.

### 143. Sensitive Context

If the user provides sensitive context, Ambitions may use it locally.

It must not expose sensitive learning in aggressive notifications, lock-screen copy, or cloud paths.
