## 0. Supreme interpretation law

Every Ambitions project, Linear issue, Codex prompt, source change, design pass, QA gate, release claim, and architecture review must be read through this lens first:

Ambitions is a private Personal Life OS for contextual life orchestration.

Its primary function is to convert messy life intent into contextual goal paths, scheduled next actions, adaptive schedule reflow, recovery moves, proof-backed progress, and user learning — locally and inspectably.

This is the highest-order product mission. Other truth files specify IA, surfaces, runtime law, implementation state, proof standards, and release gates. They must not be interpreted in a way that weakens this mission.

## 2. Required integrated function

Ambitions must not become a collection of productivity modules. It must make one integrated loop work:

- Capture common life intent.
- Understand and classify the intent.
- Route it into the right local object.
- Generate or shape a contextual goal path.
- Support one-step goals as meaningful life intent, not disposable tasks.
- Place the next action into time reality.
- Reflow the schedule when new intent enters.
- Respect protected time, energy, capacity, commitments, and user corrections.
- Recover when reality changes.
- Preserve proof, receipts, history, source, and undo/replay context.
- Learn from outcomes and corrections.
- Remain local-first and usable without account sign-in.

The launch bar is not that Ambitions has screens for these areas. The launch bar is that the integrated loop works.

## 3. Capability layers serve orchestration

Ambitions may contain first-class behavior from mature categories:

- Task execution
- Habit/ritual tracking
- Career development tracking
- Long-term goal tracking
- Scheduling
- Calendar/time management
- Reminders
- Executive-assistant follow-up/context
- Energy/capacity management
- Endless user learning
- Contextual generative goal pathing
- Schedule reflow

These must not become separate apps inside Ambitions. They are capability layers serving one Personal Life OS.

Correct interpretation:

- Tasks are execution units.
- Habits are recurring intent.
- Calendar is time reality.
- Reminders are return points.
- Goals are direction and path.
- Energy is capacity.
- Learning is personalization.
- Reflow is intelligence.
- Proof is trust.
- Ambitions orchestrates all of them.

Hard drift:

- Todo app with goals
- Calendar with tasks
- Habit tracker with streaks
- AI chatbot with productivity tools
- Dashboard with life metrics
- Executive assistant with private life graph egress
- Collection of unrelated productivity modules

## 5. Intelligence law and runtime law

The intelligence law is:

```text
Intent -> Context -> Path -> Time Fit -> Reflow -> Action -> Proof -> Learning
```

The runtime law is:

```text
Command -> Event -> Projection -> Receipt -> Replay
```

Both must be true. The intelligence law defines what Ambitions is trying to accomplish. The runtime law defines how meaningful state change becomes safe, local, inspectable, and durable.

No model, parser, semantic index, assistant behavior, planner, scheduler, or automation may bypass the runtime law.

## 6. Schedule reflow is core

Schedule reflow is not a nice-to-have. It is a primary differentiator.

When a new goal, one-step goal, reminder, habit, commitment, or constraint enters, Ambitions must reason about:

- Does this fit today?
- Does this fit this week?
- What is fixed?
- What is protected?
- What is flexible?
- What should move?
- What should shrink?
- What should defer?
- What should recover?
- What user correction applies?
- What proof/receipt is needed?
- What change set should the user approve?

A future first-class reflow implementation should produce an inspectable change set:

```text
ScheduleChangeSet
  new item
  placement proposal
  items moved
  items shrunk
  items deferred
  protected blocks preserved
  conflicts avoided
  rationale
  confidence
  user confirmation state
  receipt
  rollback plan
```

## 7. Linear and Codex issue law

Every future Linear project and issue must answer at least one of these:

- How does this improve Intent -> Context -> Path -> Time Fit -> Reflow -> Action -> Proof -> Learning?
- How does this preserve the Personal Life OS lens?
- How does this prevent drift into a commodity task/calendar/habit/chatbot/dashboard app?
- Why is this necessary for contextual life orchestration?
- What proof will show the loop improved?

If a project or issue is infrastructure-only, it must still state which part of the orchestration loop it protects or enables.

No future issue should be accepted as Codex-ready if it cannot explain its relationship to this canon, except for narrow cleanup/security/build tasks where the relationship is explicitly “does not affect product mission; preserves repo health.”

## 8. Canonical scenario probes

The following scenarios are canonical launch-alignment probes:

Long-term goal:
User captures “I want to save for a car before the baby comes.” Ambitions creates a contextual path, identifies first step, places or recommends next action, updates Today/Goals/Time/Search, and preserves receipts/proof.

One-step goal reflow:
User captures “Call pediatrician tomorrow.” Ambitions classifies it, inspects tomorrow, avoids protected/fixed blocks, proposes placement/reflow, explains the tradeoff, commits with receipt, and updates Today/Time/Search.

Habit/ritual:
User captures “Walk 20 minutes every morning.” Ambitions creates recurring intent, checks capacity, supports skip/recovery, and avoids streak pressure.

Career development:
User captures “Get promoted by next review.” Ambitions creates a career goal path, identifies skill/evidence gaps, proposes proof capture, and schedules/reflows next steps.

Correction learning:
User says “Don’t put finance stuff at night.” Ambitions stores the correction, applies it to future planning/reflow, and allows inspection/editing.

Future intelligence, product, runtime, and launch-readiness claims should be tested against scenarios like these.

## 9. Hard red product drift

Stop and report Red when work causes or promotes:

- A separate task-app center instead of Step as execution inside life orchestration.
- A separate habit-app center with streak pressure as primary value.
- A calendar clone where Time is only events instead of life/time reality.
- A reminder app where return points do not affect goals, Today, Time, proof, and learning.
- A chatbot or generic AI planner as product center.
- Executive-assistant behavior that requires private graph egress or hosted personal context.
- Schedule changes that are not inspectable, confirmable, and receipt-backed.
- Goal pathing that does not affect Today and Time.
- One-step goals that do not trigger time-fit/reflow reasoning when timing or load requires it.
- User learning that is hidden, creepy, uninspectable, or impossible to correct.
- Source Atlas/R2 receiving private life graph, private user context, inferred priorities, goals, captures, schedule assumptions, proof, receipts, or behavior patterns.
- Cloud LLMs becoming core runtime dependencies.
