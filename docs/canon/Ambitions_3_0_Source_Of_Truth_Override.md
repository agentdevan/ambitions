Status: Active canon override for Ambitions 3.0 front-end redesign

## Purpose

This document makes the Ambitions 3.0 supersession rule explicit.

Ambitions 3.0 is the current front-end redesign canon. It supersedes older conflicting front-end, visual, interaction, navigation, wording, shell, Today, Capture, Plan, Goals, You, closure, proof, receipt, and recommendation guidance wherever the 3.0 parent or linked 3.0 child docs are more recent and explicit.

This does not mean 3.0 canon is implemented. Implementation remains evidence-gated.

For Ambitions 3.0 front-end work, use this order:

## What 3.0 Supersedes When Conflicting

Ambitions 3.0 supersedes older conflicting guidance for:

- front-end layout
- surface hierarchy
- signature objects
- Today hero/rail composition
- Day Rail vs older DayTimelineRail naming
- Hero Step Panel placement
- Meridian Shell direction
- top-level screen density
- rail/node visual grammar
- Golden Launch Loop integration
- Capture placement flow
- Action Closure presentation
- proof/receipt/review presentation
- recommendation presentation
- user-facing action verbs and receipt grammar
- front-end child doc structure
- front-end build sequence
- Ambitions-native UI invention candidates where the 3.0 invention bank is more recent and explicit

---

## What 3.0 Does Not Supersede By Default

Ambitions 3.0 does not replace these older canon domains unless an active 3.0 doc explicitly says so:

- core domain object definitions
- local-first data posture
- sync/export rules
- privacy and memory confirmation policy
- sensitive Life Area policy
- permission timing
- major confirmation requirements
- trust/privacy/data controls remaining available
- roadmap/batch status
- implementation acceptance gates
- release readiness gates
- accessibility evidence requirements
- monetization policy

---

## Conflict Resolution

When documents conflict:

1. `BATCH_REGISTRY.md` decides implementation/status truth only.
2. This override and the 3.0 parent decide front-end redesign truth.
3. Linked active 3.0 child docs decide their owned surface, component, or contract.
4. `Ambitions_3_0_UI_Invention_Upgrade_Bank.md` decides validity of canonized Ambitions-native invention candidates, but does not create implementation permission by itself.
5. Domain Model decides object definitions where 3.0 has not explicitly refined front-end lifecycle or presentation.
6. Trust / Privacy / Memory decides sensitive data, memory, permission, confirmation, receipt, and removal policy where 3.0 has not explicitly refined presentation.
7. Implementation Acceptance Gates decide definition of done.
8. Older docs remain valid only where compatible.

---

## Canon vs Implementation Status

A 3.0 concept may be:

- Canonized
- Designed
- Implementation-scoped
- Implemented
- Previewed
- Tested
- Device-verified
- Release-ready

Do not collapse these statuses.

Do not claim that a 3.0 concept exists in app code until code, previews, tests, and relevant device/platform evidence support it.
