## 1. Top-level surface question doctrine

Every top-level surface must answer one dominant question on first glance.
That dominant question should be legible in the first screenful, reinforced by the hero region, and preserved through the screen's action hierarchy.

### Canonical top-level questions

- `Today` — **What matters now?**
- `Goals` — **Where am I headed?**
- `Plan` — **How does this week hold together?**
- `Insights` — **What am I learning?**
- `Profile / Trust` — **How is my system configured?**

### Doctrine implications

- no top-level surface should compete to answer two primary questions at once
- each top-level hero must privilege one dominant truth over secondary modules
- secondary modules may support the dominant question but must not dilute it
- drill-down routes may become deeper and more mixed, but the top-level shell must remain obvious
- if a surface starts feeling crowded, the fix is usually stronger prioritization and route ownership, not more summary cards

### Screen ownership guidance

- `Today` owns immediate execution truth, active recovery, and now/next framing
- `Goals` owns direction, active ambition posture, readiness, and strategic movement
- `Plan` owns week shape, available room, fixed/flexible tradeoffs, and believability
- `Insights` owns reflection, pattern recognition, neglected-area truth, and behavioral learning
- `Profile / Trust` owns appearance, integrations, sync, permissions posture, and configuration boundaries

## 2. Mobile provenance and return doctrine

Ambitions should not rely on desktop-style breadcrumbs as a primary mobile pattern.
On phone surfaces, provenance should be calm, compressed, and useful.

### Canonical mobile provenance system

Use three layers:

#### 2.1 Origin Chip
A compact provenance cue such as:
- `From Today`
- `From Plan`
- `From Goals`
- `From Widget`
- `From Notification`

Use when the user benefits from immediate awareness of how they arrived.

#### 2.2 Context Ribbon
A thin contextual structure cue such as:
- `Home > Move > Utilities`
- `Career > Certification > Exam Prep`
- `Health > Weight Loss > Meal Prep`

This is not a heavy desktop breadcrumb.
It exists to orient the user inside the object's structural context.

#### 2.3 Return Stack Memory
Preserve the route and scroll context the user came from.
Returning should feel like re-entering the prior surface state, not booting a new view tree.

### Doctrine implications

- use provenance only when it reduces ambiguity
- avoid stacking both origin and context treatment loudly in the same first screenful unless the route is genuinely deep
- preserve object-persistent transitions so the same goal, block, or recommendation feels continuous across surfaces
- external-entry routes should preserve where possible: source, reason for entry, and last local context

## 3. Consolidated product pillar decision

The newly proposed product additions should not remain as many small branded systems.
They are consolidated into five platform pillars plus two cross-cutting programs.

### 3.1 Platform pillars

#### A. Path Intelligence Layer
The canonical path and recommendation intelligence layer.

Owns:
- path drafting
- readiness and prerequisite logic
- resource and evidence packs
- decision-swing clarifications
- why-this reasoning
- recommendation confidence and uncertainty framing

Primary product role:
Help the user understand how to move toward a meaningful outcome in a way that is believable and explainable.

#### B. State Continuity Mesh
The canonical continuity and cross-device state contract.

Owns:
- near-real-time Apple-device sync expectations
- sync receipts and conflict semantics
- active-session ownership / lease behavior
- device handoff continuity
- stale-state and reconnect handling
- sync health state language

Primary product role:
Make Ambitions feel like one reliable system across iPhone, iPad, Watch, and later Mac surfaces.

#### C. Reality Model
The canonical model of real-life room, pressure, and changing conditions.

Owns:
- schedule pressure
- calendar truth
- protected time
- free-time regimes
- seasonal availability
- life-transition posture
- arrival or event-triggered timing relevance
- week and day believability truth

Primary product role:
Prevent fantasy planning and keep the product anchored to actual life conditions.

#### D. Execution Resilience Stack
The canonical adaptation and fallback layer.

Owns:
- lighter-version options
- equivalent-progress choices
- blocked-state handling
- recovery cascade logic
- preserve-state moves
- active focus continuity behavior

Primary product role:
Keep motion alive when the original plan no longer fits.

#### E. Context Vault + Signal Policy
The canonical personalization and permission boundary.

Owns:
- optional personal-context domains
- per-domain usage explanations
- signal derivation rules
- revocation and auditability
- on-device versus synced handling by data class
- calm sensitive-data posture

Primary product role:
Make personalization useful, trustworthy, and non-creepy.

### 3.2 Cross-cutting programs

#### F. Progressive Intelligence Onboarding
The staged introduction system for setup, permissions, and added intelligence.

Owns:
- low-friction first-run setup
- 60-second starting state
- progressive enrichment
- permission sequencing
- education tied to payoff
- early degraded-state explanation

#### G. Reflection OS
The calm reflective layer for learning, suggestions, and long-term truth.

Owns:
- Quiet Gaps
- Truth Mirror
- pattern narratives
- suggestion framing
- review coherence
- neglected-domain reflection

## 4. UX rules added by this addendum

### 4.1 One dominant question per top-level surface
This is mandatory, not aspirational.

### 4.2 Provenance should reduce ambiguity, not add chrome
Use Origin Chip, Context Ribbon, and Return Stack Memory selectively and deliberately.

### 4.3 Recommendation depth is tiered
Recommendation and trust depth should scale by surface:
- ambient: compact and glance-safe
- in-app primary: concise and calm
- deep trust: expandable reasoning, evidence, correction, and memory

### 4.4 Reality and resilience outrank administrative completeness
When tradeoffs appear, prefer believable execution support over extra configuration surfaces.

### 4.5 Personalization must remain optional, explicit, and inspectable
Do not bury sensitive-context usage inside opaque intelligence behavior.

### 4.6 External surfaces inherit product truth, not invent it
Widgets, Live Activities, notifications, shortcuts, and Watch flows must consume the same canonical state semantics as the app.

---

## 5. Trust rules added by this addendum

### 5.1 No silent state disagreement
When two devices disagree, the user-facing language must remain semantic and calm.

### 5.2 No hidden sensitive-context influence
If a personal signal affects recommendations materially, the user should be able to inspect that relationship.

### 5.3 No deep recommendation without provenance
Meaningful guidance should be traceable to either explicit user input, learned local history, real schedule context, or a named assumption.

### 5.4 No ambient overreach
Ambient surfaces should not expose deep reasoning, sensitive context, or high-ambiguity suggestions that belong in the main app.

### 5.5 No brittle happy-path productization
Offline, stale, unavailable, and partial-permission states must be treated as product states, not error leftovers.
