# Ambitions Signature Interface System

Status: Future Ambitions 4.0 implementation canon; SI train queued and not started until selected by global order and gates
Date: 2026-05-02

## Purpose

The Signature Interface System defines the Ambitions-native SwiftUI language for invented but believable iPhone primitives, visual operating surfaces, adaptive panels, actions, navigation, loading states, symbols, motion, receipts, and visual QA.

SI exists so later implementation work changes the product shape, not merely the styling. It must make Ambitions feel like a premium native life execution system while preserving proof boundaries.

## Status

SI is future implementation canon. It is not current app behavior until individual SI batches run, validate, commit, and record evidence. Creating this document does not start SI and does not claim release readiness.

## Relationships

- 3.0 primitives: SI composes the completed baseline primitives without rewriting product truth.
- PXOS: PXOS owns experience intent; SI owns reusable SwiftUI expression.
- PD: Product Depth composes SI primitives for drill-down flows after SI handoff.
- ME: ME gates large-file extraction before SI expands owner files.
- CS: CS gates route, raw value, external surface, import/export, and persistence compatibility.
- AOS: AOS may later expose intelligence through SI only after privacy, source-truth, fallback, and PXOS trust gates.
- REC: REC keeps release, platform, human proof, and claim boundaries evidence-bound.

## Signature Interface Principles

Premium, native iPhone-first, calm, tactile, useful, visual before reading-heavy, deep not wide, source-grounded, receipt-aware, recovery-aware, accessible, and no-shame. Today / Goals / Capture / Plan / You remain fixed.

## Information Architecture System

SI defines top-level ownership, drill-down depth, route hierarchy, push/sheet/drawer/inline expansion standards, grouped navigation lists, detail landing pages, proof/history/review entries, back navigation, cross-surface return paths, empty-state routing, and location rules.

Acceptance: no new tabs, no duplicate destinations, no orphan screens, every drill-down has a parent surface, and repeated navigation uses a reusable component or standard.

## App Shell System

The shell uses safe-area-aware compact contextual headers, coherent background behavior, restrained scroll/collapse, clear toolbar/action placement, a receipt overlay zone, accessible navigation titles without heavy visible headers, and native presentation rules.

## Surface Shell System

Top-level surfaces are visual orientation objects. Detail surfaces may be denser, but they must retain clear ownership, back paths, and proof/review entry points.

## SwiftUI Architecture Principles

Use small reusable primitives, named ownership, previews, state matrices, and projector/state/helper seams when logic should not live in views. Avoid giant owner files and one-off wrappers.

## Adaptive Panel Taxonomy

Adaptive panels include orientation, action, receipt, proof, source, recovery, setup, pressure, and drill-down panels with density states, emphasis hierarchy, zones, collapsed/expanded modes, loading/disabled states, and accessibility labels.

## Button And Action System

SI owns reusable primary, secondary, quiet tertiary, destructive, confirmation, icon-only, disabled, and loading action styles. Canonical actions include Start now, Open step, Adjust plan, Why this?, Review, Undo, Still counts, Move, Skip / Not needed, Blocked, and Waiting.

## Grouped Navigation List System

GroupedNavigationList and GroupedNavigationRow are the settings-style pattern for You and drill-down hubs. Rows support symbols, titles, subtitles, chevrons/status, disabled, blocked, setup-needed, privacy-sensitive, receipt/history, Dynamic Type, and VoiceOver labels.

## Iconography And Symbol Grammar

Prefer SF Symbols. Custom symbols require documented justification. Status, proof, recovery, source/freshness, privacy/trust, pressure/capacity, active/inactive, filled/outline, and icon-label pairing rules must be consistent and never rely on color alone.

## Loading Progress Skeleton Waiting States

SI owns initial load, refreshing source, recommendation recalculating, proof/history loading, deferred source, unavailable runtime, denied source, stale data, partial data, slow operation, disabled action pending validation, and local-only fallback states. These states must be honest and leave a next action.

## In-App Module System

SI modules are Ambitions in-app modules, not iOS widgets. Examples include Today hero, Day rail, proof preview, receipt, pressure, LifePath, setup prompt, trust summary, availability, recovery prompt, and source freshness modules. Modules have roles, density states, and drill-down entry without becoming equal-weight stacks.

## Primitive Maps

- Today: DayTimelineRail, HeroStepPanel, TrustReceiptLayer.
- Goals: LifePathView, MissionControlLane, ProofPreview.
- Capture: CaptureAtmosphereComposer and placement route reveal.
- Plan: LifeShapeMap, pressure/recovery modules, reflow decision entry.
- You: SystemProfileHeader, grouped navigation, trust summary, receipts/history entry.

Drill-downs compose the same primitives behind taps, sheets, lanes, history, proof detail, and setup flows.

## Named Primitive Concepts

DayTimelineRail 2.0, Hero Step Panel, LifePath Visualization, Mission Control Lanes, LifeShape Map, Capture Atmosphere Composer, Trust Receipt Layer, and Personal System Center Components are the core SI primitive families.

## Interaction Motion Haptics

Motion orients, confirms, or reduces uncertainty. It must not gamify. Reduced Motion equivalents are required for meaningful motion. Haptics must be purposeful and system-native.

## Accessibility Rules

VoiceOver order follows visual priority. Dynamic Type must not collapse layout into clutter. Meaning cannot depend on color or icon alone. Tap targets must feel native. Privacy-sensitive states must avoid accidental exposure.

## Preview Fixture Visual QA

Every UI-changing SI batch needs representative previews, component state matrix, screenshot evidence if scriptable, accessibility notes, reduced-motion notes, file-size report, anti-generic scan, visual QA report, and release-claim scan.

## File-Size Maintainability Boundaries

New primitives should be small enough to preview, test, and reason about. Files crossing 400 lines need review, 700 lines need extraction plan, and 1000 lines are Red unless the batch report proves a safer temporary boundary.

## Claims And Non-Claims

SI may claim source truth or a specific primitive only after the corresponding batch validates and commits. SI must not claim SI complete, PXOS implemented, PD implemented, AOS implemented, App Store readiness, TestFlight readiness, physical-device proof, public accessibility proof, signed archive proof, legal/privacy signoff, human visual approval, or release readiness.

## Anti-Generic And Anti-Card-Stack Rules

Do not create same-size stacks as the top-level structure. Do not add new tabs. Do not turn Ambitions into a task app, habit tracker, calendar clone, chatbot wrapper, notes app, project-management app, or analytics/control-panel product.

## Invented-But-Native Rubric

Score 1-5 for originality, native iPhone believability, usefulness, restraint, accessibility, emotional tone, system coherence, and maintainability. Green requires average >= 4, no category below 3, and no Red in accessibility, release-claim safety, compatibility, or file-size boundary.

## Component State Matrix

Every SI primitive must cover normal, selected, focused, loading, empty, disabled, error/degraded, privacy-sensitive, reduced-motion, and Dynamic Type states where relevant. Also cover stale source, partial source, offline/local-only, blocked, waiting, needs review, recovery, overwhelming day, setup needed, denied source, and no data yet when relevant.

## Implementation Readiness Gates

SI implementation requires PXOS complete, ME relevant gates, CS compatibility gates where touched, REC claim boundaries, accessibility/cognitive-load gates, visual QA/preview evidence, file-size/diff-size gates, anti-generic UI gates, and no-card-stack top-level gates.

## Handoff Into PD And AOS24

PD must compose SI primitives where relevant. AOS24 must depend on SI handoff if intelligence is exposed in UI. SI18 closes SI with primitive inventory, unresolved Yellow owners, PD readiness map, AOS24 implications, and rollback path.
