# Visual Recipe Short Form Template

Status: Canon template for high-specificity surface recipes

Use this template for each priority recipe.

Each section below must be written in object-specific language and must include:

- what the section must contain
- the minimum acceptable specificity
- one bad example
- one good example
- a validator hint
- the tier requirement level

If a section cannot satisfy those six fields, the recipe is too generic for final-proof authority and the validator must fail it.

## Purpose
State the user job and why this surface exists.

## Surface Hierarchy
State where the surface sits in the object tree and what it owns above and below.

## Primary Object Dependency
Name the governing object and the objects that must stay attached to it.

## Label-Off Signature
Describe the structure that still makes the surface recognizable when labels blur.

## Canonical Anatomy
Describe the visible regions in order and the meaning of each region.

## Visible Regions
List the concrete regions and what each region is allowed to show.

## Dominant Object
Name the single object that should dominate at rest.

## Supporting Objects
List the objects that support the primary object without becoming equal weight.

## Primitive Usage
Name the semantic primitives the surface is allowed to use.

## Typography Roles
Describe the weight hierarchy, emphasis rules, and collapse behavior.

## Spacing Rules
Describe the density budget, grouping logic, and touch intent.

## Material Rules
Describe ground, layer, and inspectable material semantics.

## Color / State Rules
Describe how semantic state beats color and when color may reinforce.

## Iconography
Describe which icons are allowed and what they must never mean alone.

## Chevron / Disclosure Rules
Describe when deeper inspection is allowed and how disclosure is labeled.

## Source / Trust Behavior
Describe source freshness, local runtime, and correction path behavior.

## Proof / Receipt Behavior
Describe what receipt or proof is expected and how it stays attached.

## Transaction Behavior
Describe intent, preview, commit, receipt, and undo or recovery.

## Primary Action
Describe the one dominant action at rest.

## Secondary Correction Path
Describe the visible correction, undo, or recovery path.

## Empty State
Describe the surface when nothing is yet placed.

## Loading / Unknown State
Describe the surface when source or state is unresolved.

## Error / Conflict State
Describe the surface when source, proof, or fit conflicts.

## Recovery State
Describe the surface when the user is repairing or recovering.

## VoiceOver Order
Describe the announcement order for the surface.

## Dynamic Type Behavior
Describe what remains visible when text gets large.

## Reduce Motion Behavior
Describe what replaces motion when motion is reduced.

## Reduce Transparency Behavior
Describe what happens when glass becomes opaque.

## Increase Contrast Behavior
Describe what state boundaries get stronger.

## Differentiate Without Color Behavior
Describe the non-color signals that remain.

## ADHD Density Law
Describe the top-of-surface attention budget and recovery rule.

## Native iPhone Believability Requirements
Describe why the surface still feels native on iPhone.

## Train / Source-Family Influence
Describe which source-family directions shaped the recipe.

## Source Linkage
Describe the source-link status, caveat, and debt class.

## Implementation Proof Boundary
State that design canon does not prove implementation.

## Unresolved Direction
State any open direction explicitly.

## Anti-Generic Red Flags
List the patterns that would make the surface generic.

## Forbidden Interpretations
List the meanings that must not be inferred.

## Acceptance Checklist
State the minimum checks required before a recipe can be called specific.
