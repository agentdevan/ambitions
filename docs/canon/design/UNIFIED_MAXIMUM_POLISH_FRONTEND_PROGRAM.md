## Authority and purpose

The Ambitions Unified Maximum Polish Frontend Program is the sole active
frontend design, construction, proof, integration, cutover, and closure
program. It operates beneath the supreme Owner Taste authority and the owning
product canon. It supersedes the Native Visual Foundry as a standalone program
and the sequencing in the Reconciled Flagship Reconstruction Plan.

Native Visual Foundry remains a subordinate capability inside this program. It
provides deterministic fixtures, preview and host rendering, interaction
scenarios, screenshots, and bounded native proof. It is not a design authority,
component library, independent frontend, or production renderer.

## Single source model

The program produces one frontend implementation:

- `AmbitionsPresentationContracts` owns typed presentation state, navigation,
  restoration, intents, and results;
- `AmbitionsFlagshipFoundation` owns the single Ambitions design system;
- `AmbitionsFlagshipUI` owns every canonical screen and composition;
- the Foundry host injects synthetic fixtures into those views; and
- the production app injects runtime-backed adapters into those same views.

Foundry and production render source-identical canonical UI. Only their
adapters differ. Canonical UI cannot depend on Foundry, production runtime
implementations, or the legacy production design systems.

## Component policy

Apple SwiftUI is the behavioral substrate. Ambitions creates identity through
semantic composition, hierarchy, state, continuity, and restrained atmosphere.
A shared component is earned by repeated approved consumers that share meaning,
state, lifecycle, and accessibility—not merely appearance.

At `UFP-4`, every Foundry and Maximum Polish component receives one final
disposition: `promote`, `rebuild`, `fixture-only`, `historical`, or `delete`.
General-purpose UI libraries are not baseline dependencies. An external leaf
dependency requires a proven Apple-framework gap, current license/privacy/
security review, accessibility and performance proof, a replaceable adapter,
version pinning, and a removal plan.

## Cutover and deletion law

The current production frontend is legacy in full and is not a visual reuse
source. Necessary nonvisual behavior may be extracted into a runtime-owned
module, after which the mixed legacy file is deleted. No dual renderer ships.
Rollback uses version control and the prior release, not dormant legacy code.

`UFP-7` is incomplete until a machine-verifiable zero-legacy audit shows no old
frontend source, package product, target, dependency, import, asset, route,
preview, UI test, feature flag, compatibility wrapper, or unclassified
frontend file remains.
